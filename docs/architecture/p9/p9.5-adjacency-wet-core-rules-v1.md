# P9.5 — Adjacency and Wet-Core Rules v1

## Goal

Validate semantic coherence before geometry is accepted. P9.5 separates hard blockers from soft preferences and keeps wet-core reasoning explicit, deterministic and non-normative.

## Rule model

```dart
enum TopologyRuleStrength { required, preferred, forbidden }

enum TopologyRelationKind {
  adjacency,
  openingConnection,
  circulationReachability,
  exteriorContact,
  wetCoreMembership,
  balconyAttachment,
  privacySeparation,
}

final class ApartmentTopologyRule {
  final TopologyRuleId id;
  final TopologyRuleStrength strength;
  final TopologyRelationKind kind;
  final TopologySlotSelector left;
  final TopologySlotSelector right;
}
```

Hard `required/forbidden` rules decide candidate validity. `preferred` rules feed P9.7 scoring and never make an otherwise valid candidate invalid unless a template explicitly upgrades them to hard policy.

## Required semantic rules

Every generated apartment must satisfy:

```text
entry reaches circulation/day zone without crossing a private bedroom
all habitable/service spaces are reachable from the apartment entry graph
no required relation references a missing slot
forbidden adjacency is absent
balcony/loggia attaches to an exterior-facing eligible room
bathroom/WC cannot become the only circulation bridge between unrelated rooms
private bedroom is not used as transit to another required room
```

## Wet-core model

Wet-core semantics apply to:

```text
kitchen
kitchenLiving
bathroom
wc
showerRoom
laundry when generated
```

Each template declares:

```text
wetCoreId(s)
required members
optional members
preferred members
allowed split-core count
maximum semantic graph distance between members
```

P9 v1 validates semantic compactness and adjacency/proximity in the topology graph. It does NOT claim plumbing-code compliance or calculate pipe hydraulics.

## Wet-core policies

Supported policies:

```text
singleCoreRequired
singleCorePreferred
splitCoreAllowed
splitCoreRequired
```

For `singleCoreRequired`, all wet slots must belong to one declared core and satisfy the template's required adjacency/proximity graph.

## Circulation validation

Build a graph where nodes are semantic spaces and traversable relations are opening/open-passage/circulation relations. From the entry node:

```text
BFS/DFS must reach every required interior space
```

A candidate is invalid if the only path to another space crosses a bedroom unless that exact template explicitly permits the relation, which v1 templates should not.

## Geometry-aware second pass

P9.5 has two passes:

```text
semantic pass   after grammar expansion, before geometry
geometry pass   after P9.6, verifying declared adjacency exists physically
```

The geometry pass verifies:

```text
required shared boundaries have non-zero length
forbidden physical adjacencies are absent where declared
exterior-required spaces contact candidate exterior boundary
balcony/loggia attachment is physically realizable
```

## Validation report

```dart
final class ApartmentTopologyValidationReport {
  final List<ApartmentTopologyIssue> blockers;
  final List<ApartmentTopologyIssue> warnings;
  final List<ApartmentTopologyPreferenceResult> preferences;
}
```

Issue codes are machine-stable; localized text belongs to UI.

## Fail closed

The generator must reject a candidate rather than:

```text
remove a bathroom
change a kitchen mode
ignore a forbidden relation
invent a door/opening
silently detach balcony
turn a hard rule into a score penalty
```

## Exit gate P9-G05

```text
hard vs soft rules explicit
entry reachability proven
wet-core policy explicit
semantic and geometry passes agree
invalid candidates fail closed
no normative certification claim
stable issue codes
```
