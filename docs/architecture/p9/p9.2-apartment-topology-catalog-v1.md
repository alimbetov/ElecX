# P9.2 — ApartmentTopologyCatalog v1

## Goal

Define a versioned semantic catalog of apartment topology templates. The catalog describes what an apartment topology means and what constraints it supports; it does not store final SVG drawings and does not own committed project IDs.

## Core model

```dart
final class ApartmentTopologyCatalog {
  final String catalogVersion;
  final List<ApartmentTopologyTemplate> templates;
}

final class ApartmentTopologyTemplate {
  final TemplateId templateId;
  final int templateVersion;
  final ApartmentTopologyFamilyId familyId;
  final ApartmentTopologyCompatibility compatibility;
  final List<TopologySpaceSlotSpec> spaceSlots;
  final List<TopologyRelationSpec> relations;
  final TopologyAreaProfile areaProfile;
  final CirculationPolicy circulationPolicy;
  final WetCorePolicy wetCorePolicy;
  final FacadePolicy facadePolicy;
  final TopologyLayoutGrammar layoutGrammar;
  final List<TopologyVariantSeed> variantSeeds;
}
```

## Catalog identity

```text
catalogVersion      version of complete shipped catalog
templateVersion     semantic version of one template
generatorVersion    P9 generator implementation version
```

Changing display text does not require a semantic template version bump. Changing slot structure, constraints, relations, layout grammar or area policy does.

## Space slots

Stable machine keys within a template:

```text
entry
corridor
living
bedroom:1
bedroom:2
kitchen
bathroom:1
wc:1
loggia:1
```

A slot key is NOT a `SpaceId`. It is semantic template identity used for deterministic generation, provenance and identity-reservation naming.

Each slot specifies at least:

```text
slotKey
SpaceUsage
structural type
required/optional condition
min/preferred/max area
relative area weight
minimum clear-width guidance
aspect-ratio guidance
privacy zone
wet-core membership
facade/exterior requirement
```

## Compatibility contract

Each template declares explicit support for room count, area, bathroom/WC/balcony count, kitchen/corridor/privacy modes, entry side and facade constraints.

Compatibility evaluation is pure and happens before expensive generation.

## Deterministic ordering

Canonical ordering:

```text
familyId
then templateId.value
then templateVersion
```

Variant seeds are ordered by stable `seedId`.

## Catalog validation

Fail closed on:

```text
duplicate templateId/version
duplicate slotKey
empty required-space set
relation references unknown slot
area rule references unknown slot
minArea > preferredArea > maxArea violations
non-positive areas
duplicate seed ID
unknown grammar transform
wet-core rule references non-wet slot
facade rule references impossible slot
layout grammar fails to cover required slots
```

Validation occurs once at composition/startup or fixture construction, not per card render.

## Data representation

P9 v1 may ship typed Dart constants or a declarative bundled asset decoded into typed contracts. Runtime authority is always typed `ApartmentTopologyTemplate` objects.

Forbidden authority:

```text
SVG files
localized labels
UI card order
file names
random IDs
remote API responses
```

## Catalog scope

The catalog covers the canonical families where compatible:

```text
compact
linear
corner
centralCorridor
corridorSpine
euro
openPlan
splitDayNight
```

It does not need every family for every room count; support matrices must be explicit.

## Template selection policy

If `preferredFamily == null`, all compatible families participate. If explicitly set, only that family participates; the generator must not silently ignore it.

## Candidate cache key

Pure catalog-stage cache keys may use:

```text
requestFingerprint
catalogVersion
generatorVersion
```

No persistent entity IDs.
