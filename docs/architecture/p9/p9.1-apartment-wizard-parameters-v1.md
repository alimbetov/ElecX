# P9.1 — ApartmentWizardParameters v1

## Goal

Define one immutable, strongly typed and deterministic parameter contract for apartment generation. The parameter model is the only authoritative user intent consumed by the P9 generator. Flutter controls, localized labels, form-controller state and ad-hoc maps are projections only.

P9.1 extends the accepted P8 `WizardParameters` contract and MUST NOT create a second Wizard protocol.

## Public contract

Recommended package:

```text
lib/src/application/project/wizard/apartment/
```

Recommended types:

```dart
final class ApartmentWizardParameters extends WizardParameters {
  final int habitableRoomCount;              // 1..10
  final AreaMm2? targetArea;                 // optional at edit time, required for generation
  final int bathroomCount;                   // 1..6
  final int separateWcCount;                 // 0..4
  final int balconyCount;                    // 0..4
  final ApartmentBalconyPreference balconyPreference;
  final ApartmentKitchenMode kitchenMode;
  final ApartmentCorridorMode corridorMode;
  final ApartmentPrivacyMode privacyMode;
  final ApartmentTopologyFamilyId? preferredFamily;
  final ApartmentEntrySide? preferredEntrySide;
  final Set<ApartmentFacadeSide> preferredFacadeSides;
  final ApartmentCandidateKey? selectedCandidateKey;
}
```

`AreaMm2` is an integer engineering value object. UI may display square metres, but the application contract MUST NOT use locale-formatted strings or floating-point values as identity/fingerprint input.

## Hard parameter envelope

The v1 generator accepts only bounded input:

```text
habitableRoomCount  1..10
bathroomCount       1..6
separateWcCount     0..4
balconyCount        0..4
targetArea          18..600 m² when provided
```

These are product/generator limits, not building-code declarations. Template compatibility applies stricter limits where needed.

Generation MUST require a non-null `targetArea`. The UI may temporarily hold incomplete parameters while the user edits them, but `validateParameters()` must block generation until the required generation input is complete.

## Meaning of habitableRoomCount

`habitableRoomCount` counts conventional habitable rooms only:

```text
living room
bedroom(s)
study when explicitly generated as a habitable room
```

It does NOT count:

```text
kitchen
bathroom
WC
corridor
entrance hall
wardrobe
storage
balcony/loggia
laundry
```

For `kitchenLiving`, the combined kitchen/living space counts as one habitable room. Therefore a 3-room kitchen-living apartment normally contains the combined kitchen/living room plus two additional habitable rooms.

## Validation layers

Validation is intentionally layered.

### Layer A — syntactic/domain envelope

Reject:

```text
room count outside 1..10
negative counts
bathroomCount == 0
area outside global P9 bounds
empty or unknown enum values
selectedCandidateKey with malformed canonical representation
```

### Layer B — catalog compatibility

A syntactically valid request may still have no compatible template, for example:

```text
1 habitable room + 6 bathrooms
compact family requested for 10 rooms
openPlan requested against a family that forbids it
4 balconies requested against a template with max 1
```

These conditions return typed compatibility blockers; they are not silently normalized into another request.

### Layer C — selected-candidate validity

`selectedCandidateKey` is valid only when it belongs to the exact normalized input/catalog/generator version currently being edited. Any semantic parameter change clears selection or causes validation to return `candidateSelectionStale`.

## Normalization

Normalization MUST be pure and idempotent:

```text
normalize(normalize(x)) == normalize(x)
```

Rules:

```text
preferredFacadeSides sorted by enum ordinal
set duplicates removed
preferredFamily retained exactly; never auto-substituted
selectedCandidateKey cleared when its request fingerprint differs
no hidden change of room/bathroom/balcony count
no auto-rounding of target area except unit parsing at UI boundary
```

User-entered area such as `78.5 m²` is parsed once into integer area units before it reaches `ApartmentWizardParameters`.

## Stable intent fingerprint

Introduce a canonical machine representation, for example:

```text
p9-apartment/v1|rooms=3|areaMm2=78500000|bath=2|wc=0|balcony=1|balconyPref=loggia|kitchen=kitchenLiving|corridor=compact|privacy=preferDayNightSeparation|family=*|entry=*|facades=east,south
```

`selectedCandidateKey` is NOT part of the base request fingerprint. It identifies a result of the request, not the request itself.

The fingerprint must be independent of locale, Flutter widget order, platform, map iteration order, current time, random source and persistent entity IDs.

## Defaults

Recommended v1 defaults:

```text
habitableRoomCount = 2
bathroomCount      = 1
separateWcCount    = 0
balconyCount       = 1
balconyPreference  = any
kitchenMode        = separate
corridorMode       = auto
privacyMode        = neutral
preferredFamily    = null
preferredEntrySide = null
preferredFacadeSides = {}
selectedCandidateKey = null
```

`targetArea` remains unset rather than inventing a project area.

## Exit gate P9-G01

```text
all authoritative parameters are typed
no Map<String,Object?> parameter authority exists
normalization is idempotent
request fingerprints are deterministic
invalid values fail with stable codes
selection becomes stale after semantic parameter change
no locale/platform/random/time data affects intent
```
