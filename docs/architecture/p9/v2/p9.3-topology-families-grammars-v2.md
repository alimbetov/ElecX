# P9.3 — Topology Families & Grammars v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: compatible catalog templates + normalized request  
Produces: bounded `ApartmentTopologyDraft[]`

## 1. Objective

Define topology families as deterministic semantic grammars that expand one compatible template into a bounded set of apartment topology drafts.

A family is not a picture. It is a rule system describing spatial roles, graph relations and bounded ordering/layout strategies.

## 2. Family set v1

Authoritative initial set:

```text
compact
linear
corner
centralCorridor
corridorSpine
euro
openPlan
splitDayNight
```

Recommended capability envelope:

| Family | Typical room count | Character |
|---|---:|---|
| compact | 1..3 | minimum circulation, dense service core |
| linear | 1..4 | rooms organized along one circulation line/facade logic |
| corner | 2..5 | two-direction exterior exposure |
| centralCorridor | 3..6 | central circulation node/short branches |
| corridorSpine | 4..10 | scalable circulation spine |
| euro | 1..4 | kitchen-living as day-zone anchor |
| openPlan | 1..3 | reduced partitioning in day zone |
| splitDayNight | 3..10 | explicit public/private zoning |

Template constraints remain authoritative; this table is not a substitute for P9.2 filtering.

## 3. Grammar model

Conceptually:

```dart
abstract interface class ApartmentTopologyGrammar {
  ApartmentTopologyFamily get family;

  List<ApartmentTopologyDraft> expand({
    required NormalizedApartmentRequest request,
    required ApartmentTopologyTemplate template,
    required TopologyVariantSeed seed,
  });
}
```

A draft contains semantic nodes/roles and graph intent but no final P7 canonical IDs.

```dart
final class ApartmentTopologyDraft {
  final TemplateId templateId;
  final int templateVersion;
  final ApartmentTopologyFamily family;
  final String variantSeedId;
  final List<DraftSpace> spaces;
  final List<DraftAdjacencyIntent> adjacency;
  final DraftCirculationGraph circulation;
  final DraftExteriorExposure exteriorExposure;
  final DraftWetCoreGrouping wetCore;
  final String draftFingerprint;
}
```

## 4. Space role model

Grammar works with semantic roles, not labels:

```text
entry
entranceHall
primaryDaySpace
secondaryDaySpace
kitchen
kitchenLiving
bedroom[n]
bathroom[n]
wc[n]
circulation[n]
storage[n]
balcony[n]
```

Localized names are assigned only in presentation/materialization.

## 5. Common grammar requirements

### P9.3-FR-001 — Complete requested semantics

Expansion MUST emit exactly the requested habitable-room count and requested service-space cardinalities compatible with the selected template.

### P9.3-FR-002 — Stable semantic keys

Generated draft keys MUST be deterministic:

```text
livingRoom:1
bedroom:1
bedroom:2
bathroom:1
wc:1
corridor:1
balcony:1
```

Key numbering is stable under repeated generation.

### P9.3-FR-003 — Bounded expansion

Hard bounds:

```text
max drafts per template+seed        4
max seed expansions per template   12
max raw drafts per request         64
```

If the theoretical expansion is larger, grammar MUST prune by deterministic stable order before geometry generation.

### P9.3-FR-004 — Symmetry control

Mirroring/rotation MAY create variants only when semantically meaningful for entry/facade/exposure. Equivalent symmetric duplicates MUST be eliminated by normalized draft fingerprint.

### P9.3-FR-005 — No geometry search

Grammar does not run arbitrary packing/optimization. It produces a layout skeleton/split strategy consumed by P9.6.

## 6. Family rules

### 6.1 compact

Required characteristics:

```text
entry -> entranceHall/day zone
circulation node count minimized
wet spaces grouped where possible
no long mandatory corridor spine
```

Hard suitability default: 1..3 habitable rooms unless template explicitly qualifies more.

### 6.2 linear

```text
one ordered circulation sequence
room groups attached in stable linear order
entry anchored at one end or controlled midpoint seed
exterior exposure assigned along declared facade side(s)
```

### 6.3 corner

```text
two exterior directions available
at least two habitable roles may receive distinct exposure directions
corner seed determines day/private orientation
```

### 6.4 centralCorridor

```text
one central circulation role
rooms branch from central node
branch order stable by semantic role
corridor must not become a habitable-room substitute
```

### 6.5 corridorSpine

```text
one primary spine
bounded branch nodes
scales to large room counts
wet-core group attached to spine at deterministic anchor
```

### 6.6 euro

```text
kitchenMode must be kitchenLiving unless template explicitly supports conversion path
kitchenLiving is the primary day-space anchor
private rooms attach through circulation, not through kitchen work zone
```

### 6.7 openPlan

```text
openPlan kitchen/day-zone relation explicit
reduced internal separation is semantic, not inferred from missing walls
private rooms remain distinct spaces
```

### 6.8 splitDayNight

```text
entry -> day zone / distribution
public/day subgraph distinct from private/night subgraph
bedrooms grouped in night subgraph
bathroom placement may serve night zone but cannot isolate day zone
```

## 7. Grammar condition system

Rules SHOULD be typed predicates, e.g.:

```dart
sealed class GrammarCondition {}
final class RoomCountAtLeast extends GrammarCondition { ... }
final class KitchenModeIs extends GrammarCondition { ... }
final class BalconyCountAtLeast extends GrammarCondition { ... }
```

Avoid arbitrary expression strings.

## 8. Draft fingerprint

`draftFingerprint` includes:

```text
request.intentFingerprint
templateId/version
family
seedId
ordered space semantic keys/usages
ordered adjacency intents
circulation graph
wet-core grouping
exterior exposure assignments
layout skeleton/split roles
```

It excludes final dimensions and canonical IDs.

## 9. Invariants

### P9.3-INV-001

Every declared adjacency references an existing draft space.

### P9.3-INV-002

No semantic space key occurs twice.

### P9.3-INV-003

A grammar never changes requested kitchen semantics.

### P9.3-INV-004

Bedroom/private roles are never reachable only by passing through another bedroom.

### P9.3-INV-005

Every draft has exactly one entry role/path into circulation/day space.

### P9.3-INV-006

Equivalent semantic drafts deduplicate before P9.4.

## 10. Failure codes

```text
p9.grammar.unsupported-family
p9.grammar.invalid-template-contract
p9.grammar.request-template-mismatch
p9.grammar.missing-required-role
p9.grammar.duplicate-semantic-key
p9.grammar.invalid-circulation-graph
p9.grammar.expansion-limit
```

A grammar contract violation is a developer/catalog defect, not a user correction.

## 11. NFR

### P9.3-NFR-001

Expand all compatible templates/seeds for one request p99 <= 30 ms.

### P9.3-NFR-002

Raw draft count MUST never exceed 64.

### P9.3-NFR-003

No random, clock, locale, Flutter or network dependency.

## 13. Exit gate

P9.3 is complete when all eight families have explicit grammar implementations or are explicitly absent from the v1 catalog; every enabled family has fixtures, deterministic fingerprints, bounded expansion and contract tests.
