# P9.8 — SVG / Vector Topology Renderer v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: ranked `ApartmentGeometryCandidate`  
Produces: provider-neutral vector scene + inert SVG projection

## 1. Objective

Render each apartment candidate as a deterministic diagrammatic vector preview for Wizard cards and larger preview surfaces without making rendered output authoritative.

Canonical direction:

```text
candidate geometry -> vector scene -> SVG/native paint
```

Forbidden:

```text
SVG/native paint -> parse -> canonical geometry
```

## 2. Renderer layers

### Layer A — `ApartmentTopologyVectorScene`

Provider-neutral immutable scene derived from P9.6 geometry.

### Layer B — SVG projector

Serializes scene into inert SVG.

### Layer C — Flutter/native painter

MAY paint the same scene directly without parsing SVG.

No renderer layer owns canonical project semantics.

## 3. Vector scene contract

```dart
final class ApartmentTopologyVectorScene {
  final int widthUnits;
  final int heightUnits;
  final String semanticLabelKey;
  final List<ApartmentVectorElement> elements;
  final ApartmentPreviewSummary summary;
}
```

Element roles include:

```text
interiorEnvelope
interiorSpaceRegion
exteriorAppendageRegion
internalPartition
entryMarker
interiorDoor/openPassage marker
spaceLabelAnchor
wetCore metadata
warning metadata
```

## 4. Coordinate normalization

### P9.8-FR-001

Renderer computes overall display bounds from:

```text
interiorEnvelope + exteriorAppendages
```

and maps them into stable normalized viewBox.

Recommended card viewBox:

```text
0 0 320 220
```

with fixed logical padding.

### P9.8-FR-002

Aspect ratio is preserved. X/Y are never independently stretched.

Rendered floating coordinates are presentation only and excluded from candidate fingerprints.

## 5. Interior vs appendage visual semantics

### P9.8-FR-003

Interior envelope and exterior appendages MUST be visually distinguishable by semantic style roles.

Renderer may use theme-dependent fill/stroke differences, but role identity remains stable.

Balcony/loggia cannot visually inflate the stated interior requested area.

## 6. Visual grammar

Required roles:

```text
interior outer boundary
internal partition
interior room region
balcony/loggia/terrace appendage region
entry marker
interior door/open passage marker where useful
space label anchor
selected/highlight metadata
warning marker metadata
```

Colors/theme are presentation values, not semantic state.

## 7. Space labels

Cards SHOULD show short semantic labels when legible:

```text
Living
Bed 1
Kitchen
Bath
Hall
Loggia
```

Localized labels are resolved outside authoritative scene semantics.

At small card size, text MAY be suppressed while accessible summary remains complete.

## 8. Candidate summary contract

```dart
final class ApartmentPreviewSummary {
  final int habitableRoomCount;
  final int interiorAreaDm2;
  final int exteriorAppendageAreaDm2;
  final ApartmentKitchenMode kitchenMode;
  final ApartmentTopologyFamily family;
  final int bathroomCount;
  final int balconyCount;
  final int scoreBp;
}
```

### P9.8-INV-001

`interiorAreaDm2` and `exteriorAppendageAreaDm2` are always separate values.

UI MUST NOT display their sum under the label “interior area”.

## 9. Accessibility contract

### P9.8-FR-004

Each card exposes one concise semantic description independent of SVG internals.

Example semantic content:

```text
3-room corner apartment, 78.5 square metres interior area, 4.2 square metres loggia, kitchen-living room, 1 bathroom, score 87 percent
```

RU/EN localization happens in presentation.

### P9.8-FR-005

Screen readers MUST NOT navigate every wall/edge as separate nodes.

Card is one meaningful selectable semantic entity with optional structured detail actions.

## 10. SVG security/inertness

### P9.8-INV-002

Generated SVG contains none of:

```text
<script>
on* event attributes
<foreignObject>
external URLs
network/file image href
CSS imports
embedded executable content
```

### P9.8-INV-003

All text/attribute content is escaped.

### P9.8-INV-004

SVG is generated only from bounded internal scene primitives.

## 11. Stable serialization

Emit elements in fixed order:

```text
1 interior envelope
2 interior regions sorted by semantic key
3 exterior appendages sorted by semantic key
4 internal/shared boundaries sorted by semantic segment key
5 entry/access markers sorted by generation key
6 labels sorted by semantic key
```

Attributes use fixed ordering/normalized numeric formatting.

Equivalent scenes SHOULD produce byte-identical SVG in tests.

## 12. Element count bounds

Hard v1 per-card bounds:

```text
polygons/regions <= 40
lines/polylines  <= 128
labels           <= 32
all elements     <= 256
```

Exceeding limits fails preview generation rather than emitting pathological markup.

## 13. Theme and reduced motion

Scene stores semantic roles, not hard-coded colors.

SVG MAY use `currentColor` or stable presentation classes but theme does not enter candidate semantics.

Cards are static by default. Non-essential selection/carousel transitions honor reduced-motion state. Reduced motion does not change card content, ranking or geometry.

## 14. Comparison affordances

Scene/summary MAY expose presentation metadata:

```text
interior area by space
appendage area
family
score breakdown
wet-core count
circulation ratio
warnings
```

These overlays never mutate candidate state.

## 15. Fingerprints

Renderer MAY expose `sceneFingerprint` for visual regression:

```text
candidate.geometryFingerprint
rendererVersion
ordered scene primitives
```

It is separate from canonical candidate fingerprint. Visual-only renderer change does not rewrite generation provenance.

## 16. Error taxonomy

```text
p9.render.invalid-bounds
p9.render.non-finite-projection
p9.render.element-limit
p9.render.invalid-scene-key
p9.render.summary-inconsistent

```

Renderer failure cannot partially mutate Wizard/canonical state.

## 17. NFR

### P9.8-NFR-002

One card SVG SHOULD remain < 64 KiB for bounded v1 geometry.

### P9.8-NFR-003

## 19. Exit gate

P9.8 is complete when the same P9.6 candidate feeds card/larger preview, interior vs appendage semantics are explicit, entry/access topology can be represented, SVG is inert/deterministic/bounded, RU/EN accessibility is card-level, and no rendering artifact is canonical input.
