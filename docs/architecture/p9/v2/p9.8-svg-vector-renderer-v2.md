# P9.8 — SVG / Vector Topology Renderer v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: ranked `ApartmentGeometryCandidate`  
Produces: provider-neutral vector scene + inert SVG projection

## 1. Objective

Render each apartment candidate as a deterministic diagrammatic vector preview for Wizard cards and larger preview surfaces without making rendered output authoritative.

Canonical direction:

```text
candidate geometry -> vector scene -> SVG/native paint
```

Forbidden:

```text
SVG/native paint -> parse -> canonical geometry
```

## 2. Renderer layers

### Layer A — `ApartmentTopologyVectorScene`

Provider-neutral immutable scene derived from P9.6 geometry.

### Layer B — SVG projector

Serializes scene into inert SVG.

### Layer C — Flutter/native painter

MAY paint the same scene directly without parsing SVG.

No renderer layer owns canonical project semantics.

## 3. Vector scene contract

```dart
final class ApartmentTopologyVectorScene {
  final int widthUnits;
  final int heightUnits;
  final String semanticLabelKey;
  final List<ApartmentVectorElement> elements;
  final ApartmentPreviewSummary summary;
}
```

Element roles include:

```text
interiorEnvelope
interiorSpaceRegion
exteriorAppendageRegion
internalPartition
entryMarker
interiorDoor/openPassage marker
spaceLabelAnchor
wetCore metadata
warning metadata
```

## 4. Coordinate normalization

### P9.8-FR-001

Renderer computes overall display bounds from:

```text
interiorEnvelope + exteriorAppendages
```

and maps them into stable normalized viewBox.

Recommended card viewBox:

```text
0 0 320 220
```

with fixed logical padding.

### P9.8-FR-002

Aspect ratio is preserved. X/Y are never independently stretched.

Rendered floating coordinates are presentation only and excluded from candidate fingerprints.

## 5. Interior vs appendage visual semantics

### P9.8-FR-003

Interior envelope and exterior appendages MUST be visually distinguishable by semantic style roles.

Renderer may use theme-dependent fill/stroke differences, but role identity remains stable.

Balcony/loggia cannot visually inflate the stated interior requested area.

## 6. Visual grammar

Required roles:

```text
interior outer boundary
internal partition
interior room region
balcony/loggia/terrace appendage region
entry marker
interior door/open passage marker where useful
space label anchor
selected/highlight metadata
warning marker metadata
```

Colors/theme are presentation values, not semantic state.

## 7. Space labels

Cards SHOULD show short semantic labels when legible:

```text
Living
Bed 1
Kitchen
Bath
Hall
Loggia
```

Localized labels are resolved outside authoritative scene semantics.

At small card size, text MAY be suppressed while accessible summary remains complete.

## 8. Candidate summary contract

```dart
final class ApartmentPreviewSummary {
  final int habitableRoomCount;
  final int interiorAreaDm2;
  final int exteriorAppendageAreaDm2;
  final ApartmentKitchenMode kitchenMode;
  final ApartmentTopologyFamily family;
  final int bathroomCount;
  final int balconyCount;
  final int scoreBp;
}
```

### P9.8-INV-001

`interiorAreaDm2` and `exteriorAppendageAreaDm2` are always separate values.

UI MUST NOT display their sum under the label “interior area”.

## 9. Accessibility contract

### P9.8-FR-004

Each card exposes one concise semantic description independent of SVG internals.

Example semantic content:

```text
3-room corner apartment, 78.5 square metres interior area, 4.2 square metres loggia, kitchen-living room, 1 bathroom, score 87 percent
```

RU/EN localization happens in presentation.

### P9.8-FR-005

Screen readers MUST NOT navigate every wall/edge as separate nodes.

Card is one meaningful selectable semantic entity with optional structured detail actions.

## 10. SVG security/inertness

### P9.8-INV-002

Generated SVG contains none of:

```text
<script>
on* event attributes
<foreignObject>
external URLs
network/file image href
CSS imports
embedded executable content
```

### P9.8-INV-003

All text/attribute content is escaped.

### P9.8-INV-004

SVG is generated only from bounded internal scene primitives.

## 11. Stable serialization

Emit elements in fixed order:

```text
1 interior envelope
2 interior regions sorted by semantic key
3 exterior appendages sorted by semantic key
4 internal/shared boundaries sorted by semantic segment key
5 entry/access markers sorted by generation key
6 labels sorted by semantic key
```

Attributes use fixed ordering/normalized numeric formatting.

Equivalent scenes SHOULD produce byte-identical SVG in tests.

## 12. Element count bounds

Hard v1 per-card bounds:

```text
polygons/regions <= 40
lines/polylines  <= 128
labels           <= 32
all elements     <= 256
```

Exceeding limits fails preview generation rather than emitting pathological markup.

## 13. Theme and reduced motion

Scene stores semantic roles, not hard-coded colors.

SVG MAY use `currentColor` or stable presentation classes but theme does not enter candidate semantics.

Cards are static by default. Non-essential selection/carousel transitions honor reduced-motion state. Reduced motion does not change card content, ranking or geometry.

## 14. Comparison affordances

Scene/summary MAY expose presentation metadata:

```text
interior area by space
appendage area
family
score breakdown
wet-core count
circulation ratio
warnings
```

These overlays never mutate candidate state.

## 15. Fingerprints

Renderer MAY expose `sceneFingerprint` for visual regression:

```text
candidate.geometryFingerprint
rendererVersion
ordered scene primitives
```

It is separate from canonical candidate fingerprint. Visual-only renderer change does not rewrite generation provenance.

## 16. Error taxonomy

```text
p9.render.invalid-bounds
p9.render.non-finite-projection
p9.render.element-limit
p9.render.invalid-scene-key
p9.render.summary-inconsistent
p9.render.serialization-failure
```

Renderer failure cannot partially mutate Wizard/canonical state.

## 17. Responsive rendering contract

P9.8 is governed by `02-p9-cross-platform-responsive-input-contract-v2.md`.

The **same** `ApartmentTopologyVectorScene` MUST feed every form factor.

Allowed differences:

```text
card dimensions
number of simultaneously visible cards
label density
preview viewport scale/translation
pane arrangement
```

Forbidden differences:

```text
platform-specific geometry
platform-specific candidate filtering
platform-specific candidate order
phone-specific lower-fidelity vector scene
```

### P9.8-INV-005

COMPACT/MEDIUM/EXPANDED/LARGE render the same scene semantic fingerprint for the same candidate.

## 18. Candidate-card layout policy

### COMPACT

- one primary candidate card at a time;
- explicit Previous/Next controls plus optional swipe;
- card uses full available content width within safe padding;
- labels may collapse, but accessible summary remains complete.

### MEDIUM

- one or two candidate columns depending on usable width/text scale;
- selected card may expand details below/alongside.

### EXPANDED / LARGE

- normally 2-3 columns or comparison workspace;
- selected candidate can coexist with details/score breakdown.

Candidate ordering and selection identity remain identical across layouts.

## 19. Preview viewport

Large preview uses shared `PreviewViewportState` from P9 shared contracts.

Required operations:

```text
zoomToFit
zoomIn
zoomOut
zoomAroundAnchor
pan
resetView
```

### P9.8-INV-006

Viewport scale/translation is transient presentation state and cannot alter:

```text
geometryFingerprint
candidateFingerprint
P8 reservation
canonical coordinates
```

### P9.8-INV-007

Pinch, mouse-wheel zoom and keyboard zoom must converge on the same viewport operation semantics.

## 20. Pointer / touch / stylus behavior

Renderer surfaces MUST support:

```text
mouse/trackpad  hover optional, click select, zoom/pan where enabled
touch           tap select, pinch zoom, controlled pan
stylus          precise pointer semantics; no pressure/tilt dependency in P9
keyboard        focus/select + zoom shortcuts on focused preview
```

No semantic action may exist only through hover, right-click, long press or stylus.

When a zoomed preview captures drag/pan, carousel swipe MUST NOT also consume the same pointer sequence.

## 21. Text scale and bounds

At text scale `2.0`:

- vector canvas remains visible but yields space to essential controls;
- labels MAY be suppressed inside geometry if they become illegible;
- semantic candidate summary must remain available outside canvas;
- no label overflow may clip Apply/Preview navigation;
- preview canvas is allowed to scroll/pan intentionally, but surrounding ordinary UI must reflow rather than horizontally overflow.

## 22. Pixel-vs-semantic equality

Pixel-identical raster output across Windows/macOS/Linux/Android/iOS is NOT required.

Required cross-platform equality:

```text
same candidate geometry
same ordered vector primitives
same sceneFingerprint
same semantic summary facts
```

Platform-specific font rasterization/golden snapshots may differ.

## 23. Rendering frame performance

In addition to batch SVG generation NFRs:

- continuous preview pan/zoom SHOULD target 60 fps where hardware permits;
- pointer-move/pinch frames MUST NOT rerun P9.1-P9.7;
- geometry/path caches MAY be used per immutable scene;
- candidate scene construction must not be repeated for every responsive rebuild if source fingerprint is unchanged.

## 24. NFR

### P9.8-NFR-001

Generate vector scenes + SVG for 6 candidates:

```text
p95 <= 100 ms
p99 <= 200 ms
```

### P9.8-NFR-002

One card SVG SHOULD remain < 64 KiB for bounded v1 geometry.

### P9.8-NFR-003

No backend/filesystem/browser runtime dependency.

### P9.8-NFR-004

Responsive relayout/view changes MUST NOT trigger candidate regeneration.

## 26. Exit gate

P9.8 is complete when the same P9.6 candidate feeds card/larger preview on every responsive class, interior vs appendage semantics are explicit, entry/access topology can be represented, SVG is inert/deterministic/bounded, RU/EN accessibility is card-level, preview viewport/input semantics are modality-independent, responsive relayout cannot alter candidate identity, and no rendering artifact is canonical input.
