# P9.2 — ApartmentTopologyCatalog v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: `NormalizedApartmentRequest`  
Produces: ordered compatible `ApartmentTopologyTemplate` descriptors + incompatibility reasons

## 1. Objective

Define a deterministic, versioned, self-validating semantic catalog of apartment topology templates.

The catalog is source data for generation. It is not a collection of SVG assets and it contains no Flutter widgets or localized business semantics.

## 2. Scope

P9.2 owns:

- template identity/versioning;
- family membership;
- compatibility constraints;
- semantic space recipes;
- interior-vs-appendage area participation;
- geometric min/max guidance;
- adjacency declarations;
- wet-core/circulation policies;
- bounded variant seeds;
- catalog integrity validation;
- deterministic template filtering/order.

P9.2 does not generate final geometry; P9.3 defines grammars and P9.6 realizes geometry.

## 3. Catalog model

```dart
final class ApartmentTopologyCatalog {
  final int catalogVersion;
  final List<ApartmentTopologyTemplate> templates;
}

final class ApartmentTopologyTemplate {
  final TemplateId templateId;
  final int templateVersion;
  final ApartmentTopologyFamily family;
  final ApartmentTemplateConstraints constraints;
  final List<TopologySpaceSpec> spaces;
  final List<TopologyAdjacencyRule> adjacencyRules;
  final TopologyAreaProfile areaProfile;
  final CirculationPolicy circulationPolicy;
  final WetCorePolicy wetCorePolicy;
  final List<TopologyVariantSeed> variantSeeds;
}
```

## 4. Template identity policy

### P9.2-FR-001 — Stable template identity

`templateId` remains stable across non-semantic editorial changes. Any semantic change that can alter generated output MUST increment `templateVersion`.

Version-changing examples:

```text
room role added/removed
supported request range changed
area participation/min/preferred/max changed
dimensional/aspect constraints changed
adjacency/wet-core rule changed
variant seed behavior changed
```

### P9.2-FR-002 — Catalog version

Any change to template set or compatibility/ranking-visible metadata increments `catalogVersion`.

Persisted provenance always retains the original catalog/template versions.

## 5. Template compatibility contract

Each template MUST declare explicit compatibility:

```text
supportedHabitableRoomCounts
minInteriorAreaDm2 / maxInteriorAreaDm2
supportedBathroomCounts
supportedSeparateWcCounts
supportedBalconyCounts
supportedBalconyKinds
supportedKitchenModes
supportedCorridorModes
supportedExteriorExposurePreferences
supportsDayNightSeparation
```

`supportedExteriorExposurePreferences` is candidate-local exposure topology, not real Building facade orientation.

No compatibility is inferred from template names.

## 6. Semantic space recipe

```dart
enum SpaceAreaParticipation {
  requestedInteriorArea,
  exteriorAppendage,
}

final class TopologySpaceGeometryConstraints {
  final int minShortSideMm;
  final int? minLongSideMm;
  final int minAspectBp;
  final int maxAspectBp;
  final int? minExteriorExposureMm;
  final int maxVertices;
}

final class TopologySpaceSpec {
  final String semanticKey;
  final SpaceUsage usage;
  final ProjectSpaceType type;
  final int multiplicityMin;
  final int multiplicityMax;
  final SpaceAreaParticipation areaParticipation;
  final int minAreaDm2;
  final int preferredAreaDm2;
  final int maxAreaDm2;
  final int areaWeightBp;
  final bool nearFixedArea;
  final bool requiresExteriorExposure;
  final bool wetSpace;
  final bool circulationSpace;
  final TopologySpaceGeometryConstraints geometry;
}
```

`semanticKey` MUST be stable inside a template version.

## 7. Area participation rules

### P9.2-FR-003

Interior semantic spaces use:

```text
SpaceAreaParticipation.requestedInteriorArea
```

and participate in exact P9.4 allocation of `NormalizedApartmentRequest.interiorAreaDm2`.

### P9.2-FR-004

`balcony`, `loggia`, `terrace` use:

```text
SpaceAreaParticipation.exteriorAppendage
```

and have independent min/preferred/max area. They do not consume requested interior area.

### P9.2-INV-001

A template may not mark a balcony/loggia as `requestedInteriorArea` in P9 v1.

## 8. Dimensional constraints

Area alone is insufficient to prevent unusable extreme shapes.

Every production `TopologySpaceSpec` MUST declare geometry constraints appropriate for its role.

These values are **product generation constraints**, not claims of statutory compliance.

Catalog documentation SHOULD identify their origin/rationale (product heuristic, design guideline, later normative profile, etc.).

P9.6 enforces:

```text
minShortSideMm
minLongSideMm when set
aspect ratio range
min exterior exposure length when required
maxVertices
```

No hard dimension is inferred from localized room type labels.

## 9. Variant seeds

A variant seed represents bounded structural alternatives, not random geometry.

```dart
final class TopologyVariantSeed {
  final String seedId;
  final EntrySide entrySide;
  final bool mirrored;
  final DayNightOrientation? dayNightOrientation;
  final BalconyAttachmentStrategy balconyStrategy;
  final int stableOrder;
}
```

A template SHOULD contain `1..8` seeds. Hard maximum: `12` seeds/template.

## 10. Catalog integrity

The complete catalog MUST validate before use.

### P9.2-INV-002

`templateId + templateVersion` is unique.

### P9.2-INV-003

`seedId` is unique inside one template version.

### P9.2-INV-004

All semantic space keys are unique after multiplicity expansion.

### P9.2-INV-005

For every space:

```text
0 < minArea <= preferredArea <= maxArea
minShortSideMm > 0
0 < minAspectBp <= maxAspectBp
maxVertices >= 4
```

### P9.2-INV-006

Interior template area envelope is feasible:

```text
sum(interior minima) <= maxInteriorAreaDm2
sum(interior maxima) >= minInteriorAreaDm2
```

Exterior appendages are excluded from those sums.

### P9.2-INV-007

Every adjacency rule references declared semantic roles/keys.

### P9.2-INV-008

No same-condition direct contradiction such as one pair being both required and forbidden.

### P9.2-INV-009

A template advertising `kitchenLiving` defines `SpaceUsage.kitchenLiving` rather than silently merging unrelated spaces later.

### P9.2-INV-010

A template advertising `openPlan` defines distinct kitchen/day-space roles plus explicit open-connection intent.

### P9.2-INV-011

A space requiring exterior exposure has a positive `minExteriorExposureMm` or a template-level default.

## 11. Compatibility filtering

Filtering is pure/deterministic and evaluates in stable order:

```text
room count
interior area
bathroom count
WC count
balcony count/kind
kitchen mode
corridor mode
exterior exposure preference
special preferences
```

Output:

```dart
final class TemplateCompatibility {
  final ApartmentTopologyTemplate template;
  final bool compatible;
  final List<TemplateIncompatibilityReason> reasons;
}
```

## 12. Incompatibility codes

```text
p9.catalog.room-count

p9.catalog.area-too-large

p9.catalog.wc-count
p9.catalog.balcony-count
p9.catalog.balcony-kind
p9.catalog.kitchen-mode
p9.catalog.corridor-mode
p9.catalog.exterior-exposure-preference
p9.catalog.day-night-not-supported
```

Wizard may aggregate reasons to explain unsupported combinations.

## 13. Catalog ordering

Compatible templates return in deterministic order:

```text
preferredFamily match first
family stableOrder
template stableOrder
templateId.value
templateVersion
```

Never rely on source map iteration order.

## 14. Initial catalog minimum

Production v1 SHOULD contain at least:

```text
1-room: >= 3 qualified templates/seeds across >= 2 families
2-room: >= 4 qualified templates/seeds across >= 3 families
3-room: >= 5 qualified templates/seeds across >= 3 families
4-room: >= 5 qualified templates/seeds across >= 3 families
5-room: >= 3 qualified templates/seeds across >= 2 families
6..10 room: >= 1 qualified scalable grammar family each
```

Coverage quality matters more than raw template count.

## 15. Storage/source policy

P9 v1 catalog SHOULD be application-bundled immutable typed data or a strictly typed local resource decoded before use.

It MUST NOT require:

- backend/network;
- browser storage;
- runtime AI inference.

If encoded as resource data, decoding fails closed on unknown required enum/version values.

## 16. No SVG authority

### P9.2-INV-012

Catalog entries MUST NOT use SVG path/string as authoritative room geometry/semantic topology.

Allowed:

```text
semantic topology metadata
bounded grammar hints
dimensional constraints
preview metadata derived from candidate
```

Forbidden:

```text
parse SVG -> infer rooms -> commit
```

## 17. Normative posture

P9 catalog dimensions/adjacency/wet-core policies are product generation constraints unless separately linked to an approved normative profile.

P9 MUST NOT label a generated plan “code compliant” solely because it passes catalog validation.

Future normative engines may consume the same canonical geometry and issue explicit compliance evidence.

## 18. NFR

### P9.2-NFR-001

Full v1 catalog integrity validation p99 <= 50 ms.

### P9.2-NFR-002

Filtering complete catalog for one normalized request p99 <= 10 ms.

### P9.2-NFR-003

Catalog immutable after construction.
