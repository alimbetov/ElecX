# P9.2 — ApartmentTopologyCatalog v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: `NormalizedApartmentRequest`  
Produces: ordered compatible `ApartmentTopologyTemplate` descriptors + incompatibility reasons

## 1. Objective

Define a deterministic, versioned, self-validating semantic catalog of apartment topology templates.

The catalog is source data for generation. It is not a collection of SVG assets and it is not allowed to contain Flutter widgets or localized business semantics.

## 2. Scope

P9.2 owns:

- template identity/versioning;
- family membership;
- compatibility constraints;
- semantic space recipes;
- area envelopes/weights;
- adjacency declarations;
- wet-core/circulation policies;
- bounded variant seeds;
- catalog integrity validation;
- deterministic template filtering/order.

P9.2 does not generate final geometry; that begins in P9.3/P9.6.

## 3. Catalog model

Conceptual contract:

```dart
final class ApartmentTopologyCatalog {
  final int catalogVersion;
  final List<ApartmentTopologyTemplate> templates;
}

final class ApartmentTopologyTemplate {
  final TemplateId templateId;
  final int templateVersion;
  final ApartmentTopologyFamily family;
  final ApartmentTemplateConstraints constraints;
  final List<TopologySpaceSpec> spaces;
  final List<TopologyAdjacencyRule> adjacencyRules;
  final TopologyAreaProfile areaProfile;
  final CirculationPolicy circulationPolicy;
  final WetCorePolicy wetCorePolicy;
  final List<TopologyVariantSeed> variantSeeds;
}
```

## 4. Template identity policy

### P9.2-FR-001 — Stable template identity

`templateId` is stable across non-semantic editorial changes. Any semantic template change that can alter generated candidate output MUST increment `templateVersion`.

Examples requiring version increment:

- room role added/removed;
- supported room count changed;
- area min/max/weight changed;
- adjacency changed;
- wet-core rule changed;
- variant seed behavior changed.

### P9.2-FR-002 — Catalog version

Any change to the template set or compatibility/ranking-visible metadata increments `catalogVersion`.

Old persisted provenance retains the old catalog/template versions; it is never rewritten to pretend generation used a newer catalog.

## 5. Constraint contract

Each template MUST declare explicit compatibility:

```text
supportedHabitableRoomCounts
minAreaDm2 / maxAreaDm2
supportedBathroomCounts
supportedSeparateWcCounts
supportedBalconyCounts
supportedBalconyKinds
supportedKitchenModes
supportedCorridorModes
supportedFacadePreferences
supportsDayNightSeparation
```

No compatibility is inferred from template display names.

## 6. Semantic space recipe

Each `TopologySpaceSpec` has at least:

```dart
final class TopologySpaceSpec {
  final String semanticKey;       // e.g. bedroom:1
  final SpaceUsage usage;
  final ProjectSpaceType type;
  final int multiplicityMin;
  final int multiplicityMax;
  final int minAreaDm2;
  final int preferredAreaDm2;
  final int maxAreaDm2;
  final int areaWeightBp;
  final bool requiresExteriorExposure;
  final bool wetSpace;
  final bool circulationSpace;
}
```

`semanticKey` MUST be stable inside a template version.

## 7. Variant seeds

A variant seed represents bounded structural alternatives, not random geometry.

Conceptually:

```dart
final class TopologyVariantSeed {
  final String seedId;
  final EntrySide entrySide;
  final bool mirrored;
  final DayNightOrientation? dayNightOrientation;
  final BalconyAttachmentStrategy balconyStrategy;
  final int stableOrder;
}
```

A template v1 SHOULD contain `1..8` seeds. Hard maximum: `12` seeds per template.

## 8. Catalog integrity

The complete catalog MUST validate before use.

### P9.2-INV-001

`templateId + templateVersion` is unique.

### P9.2-INV-002

`seedId` is unique inside one template version.

### P9.2-INV-003

All semantic space keys are unique after multiplicity expansion.

### P9.2-INV-004

For every space:

```text
0 < minArea <= preferredArea <= maxArea
```

### P9.2-INV-005

A template area envelope MUST be feasible:

```text
sum(space minimums) <= template maxArea
sum(space maximums) >= template minArea
```

### P9.2-INV-006

Every adjacency rule references declared semantic roles/keys.

### P9.2-INV-007

Required adjacency graph cannot contain an impossible direct contradiction such as the same pair being both `required` and `forbidden` under the same condition.

### P9.2-INV-008

A template that advertises `kitchenLiving` MUST define a `SpaceUsage.kitchenLiving` semantic path rather than silently combining unrelated spaces later.

## 9. Compatibility filtering

Filtering is pure and deterministic.

For each template, evaluate constraints in a stable order:

```text
room count
area
bathroom count
WC count
balcony count/kind
kitchen mode
corridor mode
facade preference
special preferences
```

Output:

```dart
final class TemplateCompatibility {
  final ApartmentTopologyTemplate template;
  final bool compatible;
  final List<TemplateIncompatibilityReason> reasons;
}
```

Reasons use stable machine codes.

## 10. Incompatibility codes

```text
p9.catalog.room-count
p9.catalog.area-too-small
p9.catalog.area-too-large
p9.catalog.bathroom-count
p9.catalog.wc-count
p9.catalog.balcony-count
p9.catalog.balcony-kind
p9.catalog.kitchen-mode
p9.catalog.corridor-mode
p9.catalog.facade-preference
p9.catalog.day-night-not-supported
```

The Wizard can aggregate these reasons to explain why no candidate exists.

## 11. Catalog ordering

Compatible templates MUST be returned in deterministic order:

```text
preferredFamily match first
family stableOrder
then template stableOrder
then templateId.value
then templateVersion
```

Do not rely on source map iteration order.

## 12. Initial catalog minimum

Production v1 SHOULD contain at least:

```text
1-room: >= 3 qualified templates/seeds across >= 2 families
2-room: >= 4 qualified templates/seeds across >= 3 families
3-room: >= 5 qualified templates/seeds across >= 3 families
4-room: >= 5 qualified templates/seeds across >= 3 families
5-room: >= 3 qualified templates/seeds across >= 2 families
6..10 room: at least one qualified scalable grammar family each
```

The acceptance criterion is coverage quality, not raw asset count.

## 13. Storage / source policy

P9 v1 catalog SHOULD be application-bundled immutable Dart/domain data or a strictly typed local resource decoded before use.

It MUST NOT require:

- backend calls;
- network availability;
- browser storage;
- runtime AI inference.

If encoded as JSON/resource data, decoding MUST produce the same typed model and fail closed on unknown required enum values/version mismatch.

## 14. No SVG authority

### P9.2-INV-009

Catalog entries MUST NOT use an SVG path/string as authoritative room geometry or semantic topology.

Allowed:

```text
semantic topology metadata
bounded grammar hints
preview metadata derived from candidate
```

Forbidden:

```text
parse SVG -> infer rooms -> commit
```

## 15. NFR

### P9.2-NFR-001

Full catalog integrity validation p99 <= 50 ms for the v1 catalog on CI reference hardware.

### P9.2-NFR-002

Filtering the complete v1 catalog for one normalized request p99 <= 10 ms.

### P9.2-NFR-003

Catalog data is immutable after construction.

## 18. Exit gate

P9.2 is complete when:

- catalog model is typed/versioned/immutable;
- all templates pass integrity validation;
- compatibility filtering returns stable reasons/order;
- room-count coverage 1..10 is proven by tests;
- no SVG/backend/locale dependency exists;
- focused P9.2 qualification passes.
