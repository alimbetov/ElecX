# P9.12 — Generation Provenance v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: committed/frozen P9 generation identity  
Produces: persisted generation manifest + entity-level provenance baseline

## 1. Objective

Persist enough typed lineage to answer, after save/reopen:

```text
Who generated this entity?
From which catalog/template/family/variant?
With which generator/scoring versions?
Which user intent/candidate was committed?
Which generated fields have since been overridden?
Is this entity locked from future regeneration?
```

P9.12 closes audit finding **A09** and establishes the data contract required by future P15 selective regeneration.

P9.12 does not implement regeneration itself.

## 2. Canonical ownership

Provenance is canonical project state owned by the ProjectAggregate / persisted project document.

It MUST NOT live only in:

- Wizard session;
- UI state;
- logs;
- SVG metadata;
- transient analytics.

## 3. Generation manifest

One confirmed apartment generation creates one `GenerationManifest`.

Conceptual:

```dart
final class GenerationManifest {
  final int provenanceSchemaVersion;
  final GenerationId generationId;
  final String originType; // typed enum in implementation, wizard
  final TemplateId providerTemplateId;
  final int providerTemplateVersion;
  final int catalogVersion;
  final TemplateId apartmentTemplateId;
  final int apartmentTemplateVersion;
  final String familyId;
  final String variantSeedId;
  final String generatorVersion;
  final String scoringProfileVersion;
  final String allocatorVersion;
  final String geometryAlgorithmVersion;
  final String normalizedIntentFingerprint;
  final String selectedCandidateFingerprint;
  final ProjectId projectId;
  final BuildingId buildingId;
  final LevelId levelId;
  final ZoneId apartmentZoneId;
  final List<EntityId> generatedEntityIds;
}
```

All version strings/IDs are stable machine semantics, not localized text.

## 4. Entity provenance

Every generated Zone/Space and other generated entity that may participate in later regeneration has provenance:

```dart
final class EntityGenerationProvenance {
  final EntityId entityId;
  final GenerationId generationId;
  final String generationKey;
  final Set<PropertyKey> generatedProperties;
  final Set<PropertyKey> overriddenProperties;
  final bool lockedFromRegeneration;
  final String generatedBaselineFingerprint;
}
```

Examples `generationKey`:

```text
zone:apartment
space:bedroom:1
space:kitchenLiving:1
boundary:bedroom:1
opening:entry:1
```

`generationKey` is stable across deterministic regeneration of the same semantic role and is not the same as persistent EntityId.

## 5. PropertyKey contract

P9.12 SHOULD introduce/reuse typed `PropertyKey`, not arbitrary display strings.

Minimum generated property set for Space-like entities:

```text
name
spaceType
spaceUsage
geometry
zoneMembership
openingRelations
adjacencyRelations
```

Exact ownership may differ by entity type.

A `PropertyKey` value is schema/version controlled.

## 6. Generated baseline

### P9.12-FR-001

For each generated entity, provenance records which properties were generator-owned at commit.

### P9.12-FR-002

`generatedBaselineFingerprint` is computed from normalized generated values for those properties.

P9 v2 MAY store compact typed baseline values for properties required by future three-way merge, but it MUST NOT clone the entire ProjectAggregate as provenance.

Recommended:

```dart
final class GeneratedPropertyBaseline {
  final PropertyKey key;
  final NormalizedPropertyValue value;
}
```

for generated properties where later merge needs old baseline.

## 7. Override tracking

P15 will perform selective regeneration, but override information must not be lost between P9 and P15.

### P9.12-FR-003

Normal canonical authoring commands that modify a generated entity MUST have a provenance hook capable of marking affected generated `PropertyKey`s as overridden.

Minimum P9 coverage after apartment commit:

```text
rename Space              -> name overridden
change SpaceUsage         -> spaceUsage overridden
change boundary geometry  -> geometry overridden
manual lock action        -> lockedFromRegeneration=true
```

If a property changes back exactly to generated baseline, implementation MAY clear override only through explicit deterministic baseline comparison; it MUST NOT guess from display text.

### P9.12-INV-001

Manual entity edits never change `generationId` or `generationKey` unless the entity is explicitly detached from generation provenance.

## 8. Lock semantics

`lockedFromRegeneration=true` means future P15 regeneration must preserve the entity by default and surface conflict/locked status rather than overwrite it.

P9 UI does not need a full regeneration UI, but the persisted field and application command contract must exist if exposed.

## 9. Manifest/entity consistency

### P9.12-INV-002

Every `EntityGenerationProvenance.generationId` resolves to exactly one manifest.

### P9.12-INV-003

Manifest `generatedEntityIds` and provenance store agree for the generation operation.

### P9.12-INV-004

Generated `generationKey` is unique within one generation for one entity semantic owner.

### P9.12-INV-005

`overriddenProperties` is always a subset of meaningful/generated properties for that entity type unless an explicit extension schema supports more.

## 10. Candidate traceability

Manifest stores exact:

```text
normalizedIntentFingerprint
selectedCandidateFingerprint
catalog/template/generator/scoring versions
```

This proves what the user previewed/accepted even if current catalog later changes.

SVG fingerprint is not provenance authority.

## 11. Persistence schema

P9.12 extends `ProjectDocumentCodec` / repository document shape through a versioned migration.

Requirements:

- old projects with no generation provenance load deterministically with empty provenance state;
- P9-generated projects save/reopen without provenance loss;
- unknown future provenance schema fails according to repository compatibility policy, never silently truncates known required data;
- JSON legacy adapter and future Drift boundary use the same application/domain model.

## 12. Undo/Redo

### P9.12-FR-004

Apartment generation Undo removes its manifest/entity provenance atomically with generated entities.

### P9.12-FR-005

Redo restores the same `GenerationId`, manifest and entity provenance associated with the original committed change.

### P9.12-FR-006

Manual edit Undo/Redo updates `overriddenProperties` consistently with the restored canonical field state.

## 13. Delete semantics

If a generated entity is manually deleted:

- canonical delete wins;
- provenance entry is removed/tombstoned according to future regeneration design;
- manifest historical trace MAY retain a generation-key tombstone or generated identity list if required by P15;
- behavior MUST be explicit, not leave a dangling provenance reference.

Recommended P9 v2: retain manifest; remove active entity provenance; record `removedGenerationKeys` in manifest generation state for future conflict-aware regeneration.

## 15. NFR

### P9.12-NFR-001

Provenance overhead for one apartment SHOULD remain small relative to canonical geometry; no duplicate full geometry graph.

### P9.12-NFR-002

Manifest/provenance validation for 10k generated entities p95 <= 100 ms on CI reference hardware.

### P9.12-NFR-003

No locale/UI/network dependency.

## 17. Exit gate

P9.12 is complete when A09 is CLOSED: generation lineage is typed/persisted/versioned, exact request/candidate versions are traceable after reopen, generated entities have stable generation keys, core manual edits can mark field overrides, Undo/Redo is consistent, and validation rejects dangling/inconsistent provenance.
