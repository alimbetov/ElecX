# P9.1 — ApartmentWizardParameters v2

Status: **READY FOR IMPLEMENTATION**  
Depends on: P8 `WizardParameters`, `WizardTargetContext`  
Produces: `NormalizedApartmentRequest` and provider-safe selection wrapper

## 1. Objective

Define immutable, strongly typed apartment-generation input that separates:

```text
A. user semantic request
B. transient candidate-card selection
```

This separation is mandatory because P9.2..P9.8 generate/rank candidates from user intent, while P9.9/P8 Preview must commit the exact card selected by the user.

No later stage may read widget state or guess which candidate was selected.

## 2. Scope

P9.1 owns:

- raw typed user request contract;
- normalization;
- syntactic/semantic request validation;
- explicit target-level validation inputs;
- deterministic intent fingerprint;
- typed candidate-selection reference used by the P8 provider wrapper;
- stable machine-readable validation codes.

P9.1 does **not** decide whether a topology template exists. Catalog compatibility is P9.2.

## 3. Public contracts

### 3.1 User request

```dart
enum ApartmentKitchenMode { separate, kitchenLiving, openPlan }
enum ApartmentCorridorMode { auto, compact, central, minimal }
enum ApartmentFacadePreference { any, oneSide, corner, oppositeSides }
enum ApartmentBalconyKind { none, balcony, loggia, either }

final class ApartmentRequestInput {
  final int habitableRoomCount;        // 1..10
  final int approximateAreaDm2;        // required in v1 production UI
  final int bathroomCount;             // >= 1
  final int separateWcCount;            // >= 0
  final int balconyCount;              // >= 0
  final ApartmentBalconyKind balconyKind;
  final ApartmentKitchenMode kitchenMode;
  final ApartmentCorridorMode corridorMode;
  final ApartmentFacadePreference facadePreference;
  final ApartmentTopologyFamily? preferredFamily;
  final bool preferDayNightSeparation;
}
```

`approximateAreaDm2` uses integer square-decimetres (`78.5 m² = 7850 dm²`). UI converts localized text before constructing this object.

### 3.2 Candidate selection

```dart
final class ApartmentCandidateSelection {
  final String candidateFingerprint;
  final String templateIdValue;
  final int templateVersion;
  final String variantSeedId;
}
```

Selection identifies one exact candidate from the current candidate set. It contains no canonical project entity IDs.

### 3.3 P8 provider parameter wrapper

```dart
final class ApartmentWizardParameters extends WizardParameters {
  final ApartmentRequestInput request;
  final ApartmentCandidateSelection? selection;
}
```

`selection == null` is valid while editing/generating cards, but blocks P8 Preview/Apply.

The normalized user `intentFingerprint` is derived from `request` only. Selection has its own exact candidate fingerprint and MUST NOT be folded into user intent identity.

## 4. Production defaults

Defaults are explicit and versioned by generator defaults, never inferred from locale.

Recommended v1 defaults:

```text
habitableRoomCount        2
approximateAreaDm2        6000  (60.0 m²)
bathroomCount             1
separateWcCount           0
balconyCount              0
balconyKind               either
kitchenMode               separate
corridorMode              auto
facadePreference          any
preferredFamily           null
preferDayNightSeparation  false
selection                 null
```

If a default changes normalized user intent for a newly opened Wizard, `generatorVersion` MUST change.

## 5. Functional requirements

### P9.1-FR-001 — Typed request

Authoritative request parameters MUST be typed fields/enums. `Map<String,Object?>`, localized labels and free-form option strings are forbidden as the domain API.

### P9.1-FR-002 — Habitable room semantics

`habitableRoomCount` counts conventional habitable rooms only.

```text
livingRoom   counts
bedroom      counts
office/study counts only when emitted as one requested habitable room
kitchen      does not count
bathroom     does not count
corridor     does not count
balcony      does not count
```

For `kitchenLiving`, the combined kitchen-living room counts as one habitable room.

### P9.1-FR-003 — Production area is explicit

P9 v1 production UI MUST require `approximateAreaDm2`.

Compatibility/test APIs MAY support a template-default mode only as a distinct typed mode; `null` must not have ambiguous meaning.

### P9.1-FR-004 — Global sanity ranges

Before catalog compatibility:

```text
habitableRoomCount  1..10
area                 1500..50000 dm² (15..500 m²)
bathroomCount        1..6
separateWcCount      0..4
balconyCount         0..6
```

These are product sanity bounds, not architectural normative limits. Template-specific limits remain P9.2/P9.3 concerns.

### P9.1-FR-005 — Cross-field validation

At minimum:

```text
separateWcCount > 0 requires bathroomCount >= 1
balconyCount == 0 normalizes balconyKind to none
preferredFamily is preference, never forced validity
openPlan must not be silently converted to kitchenLiving
```

### P9.1-FR-006 — Explicit Level target

Production apartment insertion supports `LevelWizardTarget` only in P9 v1.

P9.1 validates target scope `level`; target existence/occupancy is revalidated in P9.9/P9.11 against current canonical state.

### P9.1-FR-007 — Canonical normalization

Normalization MUST:

1. validate primitive ranges;
2. normalize only semantically irrelevant combinations;
3. preserve every user semantic choice;
4. output no locale/UI dependencies;
5. serialize fields in fixed canonical order.

### P9.1-FR-008 — Intent fingerprint

`NormalizedApartmentRequest.intentFingerprint` uses only normalized request semantics.

Canonical payload order:

```text
schemaVersion
habitableRoomCount
approximateAreaDm2
bathroomCount
separateWcCount
balconyCount
balconyKind
kitchenMode
corridorMode
facadePreference
preferredFamily?
preferDayNightSeparation
```

Hash SHOULD be SHA-256 over canonical UTF-8 serialization.

### P9.1-FR-009 — Selection invalidation

Any change that changes `intentFingerprint` MUST clear `ApartmentCandidateSelection` and invalidate the prior candidate set.

Presentation-only changes (theme, hover, card expansion, locale) MUST NOT clear a still-valid selection.

### P9.1-FR-010 — Exact selection identity

Selection MUST contain the exact `candidateFingerprint` plus enough versioned template/seed identity for diagnostics/stale detection. P9.9 resolves it against the current candidate set and fails closed when absent.

## 6. Normalized request contract

```dart
final class NormalizedApartmentRequest {
  final int schemaVersion;
  final int habitableRoomCount;
  final int areaDm2;
  final int bathroomCount;
  final int separateWcCount;
  final int balconyCount;
  final ApartmentBalconyKind balconyKind;
  final ApartmentKitchenMode kitchenMode;
  final ApartmentCorridorMode corridorMode;
  final ApartmentFacadePreference facadePreference;
  final ApartmentTopologyFamily? preferredFamily;
  final bool preferDayNightSeparation;
  final String intentFingerprint;
}
```

This object is immutable and is the cache-key/request input for pure P9.2..P9.8 stages.

## 7. Invariants

### P9.1-INV-001

Equivalent user semantics normalize to byte-identical canonical serialization.

### P9.1-INV-002

No normalized field depends on RU/EN presentation text.

### P9.1-INV-003

Normalization never invents a room count, area, kitchen mode or bathroom count not requested by the user.

### P9.1-INV-004

Whitespace/decimal display formatting before UI conversion cannot change normalized semantics after typed conversion.

### P9.1-INV-005

`intentFingerprint` excludes ProjectId, LevelId, candidate selection and all reserved entity IDs.

### P9.1-INV-006

Selection does not allocate canonical IDs and does not mutate canonical state.

### P9.1-INV-007

A selection from request fingerprint A cannot be reused after request fingerprint B becomes current.
