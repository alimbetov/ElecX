# P9.1 — ApartmentWizardParameters v2

Status: **READY FOR IMPLEMENTATION**  
Depends on: P8 `WizardParameters`, `WizardTargetContext`  
Produces: `NormalizedApartmentRequest`

## 1. Objective

Define one immutable, strongly typed apartment-generation request that is independent from widgets, locale, SVG and persistence implementation.

P9.1 is complete only when every later stage can consume the normalized request without reading UI state or guessing semantics.

## 2. Scope

P9.1 owns:

- raw typed request contract;
- normalization;
- syntactic/semantic parameter validation;
- explicit target-level validation inputs;
- deterministic intent fingerprint;
- stable machine-readable validation codes.

P9.1 does **not** decide whether a topology template exists. Catalog compatibility is P9.2.

## 3. Public contract

Conceptual API:

```dart
enum ApartmentKitchenMode { separate, kitchenLiving, openPlan }
enum ApartmentCorridorMode { auto, compact, central, minimal }
enum ApartmentFacadePreference { any, oneSide, corner, oppositeSides }

enum ApartmentBalconyKind { none, balcony, loggia, either }

final class ApartmentWizardParameters extends WizardParameters {
  final int habitableRoomCount;        // 1..10
  final int approximateAreaDm2;        // required in v1 production UI
  final int bathroomCount;             // >= 1
  final int separateWcCount;            // >= 0
  final int balconyCount;              // >= 0
  final ApartmentBalconyKind balconyKind;
  final ApartmentKitchenMode kitchenMode;
  final ApartmentCorridorMode corridorMode;
  final ApartmentFacadePreference facadePreference;
  final ApartmentTopologyFamily? preferredFamily;
  final bool preferDayNightSeparation;
}
```

`approximateAreaDm2` is integer square-decimetres (`78.5 m² = 7850 dm²`). UI converts from localized text before constructing the request.

## 4. Production defaults

Defaults MUST be explicit and versioned by generator defaults, never inferred from locale.

Recommended v1 defaults:

```text
habitableRoomCount        2
approximateAreaDm2        6000  (60.0 m²)
bathroomCount             1
separateWcCount           0
balconyCount              0
balconyKind               either
kitchenMode               separate
corridorMode              auto
facadePreference          any
preferredFamily           null
preferDayNightSeparation  false
```

If product design changes a default that changes normalized intent, `generatorVersion` MUST change.

## 5. Functional requirements

### P9.1-FR-001 — Typed request

Authoritative parameters MUST be represented by typed fields/enums. `Map<String,Object?>`, localized labels and free-form option strings are forbidden as the domain API.

### P9.1-FR-002 — Habitable room semantics

`habitableRoomCount` counts conventional habitable rooms only.

Examples:

```text
livingRoom   counts
bedroom      counts
office/study counts only when emitted as one requested habitable room
kitchen      does not count
bathroom     does not count
corridor     does not count
balcony      does not count
```

For `kitchenLiving`, the combined kitchen-living room counts as one habitable room.

### P9.1-FR-003 — Production area is explicit

P9 v1 production UI MUST require `approximateAreaDm2`.

Compatibility/test APIs MAY support a template-default mode, but it must be a distinct typed mode, not `null` meaning multiple things.

### P9.1-FR-004 — Global sanity ranges

Before catalog compatibility:

```text
habitableRoomCount  1..10
area                 1500..50000 dm² (15..500 m²)
bathroomCount        1..6
separateWcCount      0..4
balconyCount         0..6
```

These are product sanity bounds, not architectural normative limits. Template-specific limits remain P9.2/P9.3 concerns.

### P9.1-FR-005 — Cross-field validation

At minimum:

```text
separateWcCount > 0 requires bathroomCount >= 1
balconyCount == 0 makes balconyKind semantically normalized to none
preferredFamily is a preference, never a forced invalid selection
openPlan must not be silently converted to kitchenLiving
```

### P9.1-FR-006 — Explicit Level target

Production apartment insertion supports `LevelWizardTarget` only in P9 v1.

P9.1 validates that target scope is `level`; target occupancy validation occurs again at P9.9/P9.11 against current canonical state.

### P9.1-FR-007 — Canonical normalization

Normalization MUST:

1. validate primitive ranges;
2. normalize semantically irrelevant combinations;
3. preserve every user semantic choice;
4. output a value with no locale/UI dependencies;
5. produce fields in fixed canonical order.

### P9.1-FR-008 — Intent fingerprint

`NormalizedApartmentRequest` exposes `intentFingerprint` based only on normalized semantics.

Canonical fingerprint payload order:

```text
schemaVersion
habitableRoomCount
approximateAreaDm2
bathroomCount
separateWcCount
balconyCount
balconyKind
kitchenMode
corridorMode
facadePreference
preferredFamily?
preferDayNightSeparation
```

Hash algorithm SHOULD be SHA-256 over UTF-8 canonical serialization.

## 6. Normalized contract

```dart
final class NormalizedApartmentRequest {
  final int schemaVersion;
  final int habitableRoomCount;
  final int areaDm2;
  final int bathroomCount;
  final int separateWcCount;
  final int balconyCount;
  final ApartmentBalconyKind balconyKind;
  final ApartmentKitchenMode kitchenMode;
  final ApartmentCorridorMode corridorMode;
  final ApartmentFacadePreference facadePreference;
  final ApartmentTopologyFamily? preferredFamily;
  final bool preferDayNightSeparation;
  final String intentFingerprint;
}
```

This object is immutable and safe to use as the cache key component for pure catalog/generator stages.

## 7. Invariants

### P9.1-INV-001

Equivalent user semantics MUST normalize to byte-identical canonical serialization.

### P9.1-INV-002

No normalized field may depend on RU/EN presentation text.

### P9.1-INV-003

Normalization never invents a room count, area, kitchen mode or bathroom count not requested by the user.

### P9.1-INV-004

Changing only whitespace/decimal display formatting before UI conversion cannot change normalized semantics.

### P9.1-INV-005

`intentFingerprint` excludes `ProjectId`, `LevelId` and any newly reserved entity IDs. Target identity is part of later candidate/commit context, not user intent.

## 8. Error taxonomy

Stable validation codes:

```text
p9.parameters.unsupported-target
p9.parameters.room-count-out-of-range
p9.parameters.area-out-of-range
p9.parameters.bathroom-count-out-of-range
p9.parameters.wc-count-out-of-range
p9.parameters.balcony-count-out-of-range
p9.parameters.invalid-balcony-kind
p9.parameters.invalid-combination
```

Validation returns all independently actionable issues where practical rather than fail-first.

## 9. Suggested user corrections

Errors MAY include typed suggestions:

```text
field
currentValue
nearestAllowedValue/range
reasonCode
```

Suggestions MUST NOT mutate input automatically.

## 10. NFR

### P9.1-NFR-001

Normalization + validation p99 <= 5 ms for one request in the CI reference environment.

### P9.1-NFR-002

No allocation of canonical project entity IDs.

### P9.1-NFR-003

No filesystem/network/Flutter rendering dependency.

## 11. Acceptance matrix

```text
P9.1-AT-001  1-room minimum request normalizes
P9.1-AT-002  10-room maximum request normalizes
P9.1-AT-003  area below/above sanity range fails
P9.1-AT-004  RU and EN input presentation map to same typed normalized request
P9.1-AT-005  balconyCount=0 normalizes balconyKind deterministically
P9.1-AT-006  kitchenLiving remains distinct from separate/openPlan
P9.1-AT-007  same request repeated 10k times yields same fingerprint
P9.1-AT-008  non-Level target fails before generation
P9.1-AT-009  changing one semantic field changes fingerprint
P9.1-AT-010  target IDs do not change intent fingerprint
```

- requirement IDs trace to tests;
- fingerprint canonicalization is documented and tested;
- no widget owns authoritative parameter semantics;
- no permanent identity is allocated;
- `dart format`, `flutter analyze`, focused P9.1 tests PASS.
