# P9.4 — Deterministic Area Fitting v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: `ApartmentTopologyDraft` + template area profile + normalized request  
Produces: `AreaFittedTopologyDraft`

## 1. Objective

Allocate the requested apartment area across semantic spaces deterministically, without nonlinear solvers, random search or floating-point instability.

The result must be feasible, explainable and reproducible across supported native platforms.

## 2. Core data model

```dart
final class SpaceAreaConstraint {
  final String semanticKey;
  final int minAreaDm2;
  final int preferredAreaDm2;
  final int maxAreaDm2;
  final int weightBp;
  final bool nearFixed;
}

final class FittedSpaceArea {
  final String semanticKey;
  final int areaDm2;
}

final class AreaFittedTopologyDraft {
  final ApartmentTopologyDraft draft;
  final int requestedAreaDm2;
  final List<FittedSpaceArea> spaces;
  final int allocatedAreaDm2;
  final int residualDm2;
  final String areaFitFingerprint;
}
```

All calculations are integer.

## 3. Functional requirements

### P9.4-FR-001 — Exact accounting

For an accepted candidate:

```text
sum(fitted space areas) == requestedAreaDm2
residualDm2 == 0
```

If exact distribution is impossible under declared constraints and rounding quantum, the candidate is rejected.

### P9.4-FR-002 — Minimums first

Initialize each space to `minAreaDm2`.

If:

```text
sum(minAreaDm2) > requestedAreaDm2
```

reject with `p9.area.request-below-minimum`.

### P9.4-FR-003 — Preferred allocation phase

Remaining area is distributed toward `preferredAreaDm2` using deterministic weighted water-filling.

Priority is controlled by explicit `weightBp` and stable semantic-key tie-break.

### P9.4-FR-004 — Maximum expansion phase

After all preferred targets are reached, remaining area may expand spaces toward `maxAreaDm2`, again using deterministic weights.

If:

```text
sum(maxAreaDm2) < requestedAreaDm2
```

reject with `p9.area.request-above-maximum`.

### P9.4-FR-005 — Near-fixed service spaces

Templates MAY mark service spaces as `nearFixed`.

Near-fixed spaces receive allocation only up to their preferred target before flexible habitable spaces absorb additional area, unless all flexible spaces reach max.

### P9.4-FR-006 — Stable remainder allocation

Integer division remainders are assigned one quantum at a time in stable order:

```text
higher unmet weighted priority
then semanticKey lexical order
```

No iteration over unordered maps/sets is allowed to decide remainder ownership.

### P9.4-FR-007 — Area quantum

Default v1 allocation quantum is `1 dm² = 0.01 m²`.

Geometry stage may realize dimensions on a coarser `10 mm` grid while keeping area-fit accounting exact within its own documented geometric tolerance.

## 4. Deterministic algorithm

Reference algorithm:

```text
INPUT requestedArea, constraints[]

1 validate constraints
2 allocate every space = min
3 remaining = requested - sum(min)
4 phase A: distribute remaining toward preferred
5 phase B: distribute remaining toward max
6 assign deterministic integer remainders
7 if remaining != 0 -> reject
8 emit ordered fitted areas
9 compute areaFitFingerprint
```

Weighted allocation for one phase:

```text
eligible = spaces below phase target
while remaining > 0 and eligible not empty:
  compute unmet capacity
  allocate proportional integer shares by weight
  distribute leftover quanta by stable priority
  remove spaces that hit target
```

Implementation MUST guard against a loop where proportional shares all round to zero; in that case deterministic one-quantum distribution progresses the algorithm.

## 5. Constraint validation

For each space:

```text
min > 0
min <= preferred <= max
weightBp > 0
```

For the template:

```text
sum weights within safe integer range
semantic keys unique
```

## 6. Fingerprint

`areaFitFingerprint` includes:

```text
draftFingerprint
requestedAreaDm2
ordered semanticKey -> allocatedAreaDm2
allocatorVersion
```

Any algorithm change that can modify allocation for unchanged inputs requires `allocatorVersion`/generator version bump.

## 7. Invariants

### P9.4-INV-001

Every accepted fitted space satisfies:

```text
min <= fitted <= max
```

### P9.4-INV-002

Total allocated area equals requested area exactly in allocation units.

### P9.4-INV-003

Increasing requested area without changing constraints MUST NOT decrease any space below its previous minimum; monotonic per-space growth is preferred but not required across phase/tie changes unless explicitly tested by profile.

### P9.4-INV-004

Same ordered or permuted input constraints yield the same semantic allocation after canonical sorting.

### P9.4-INV-005

No floating-point arithmetic controls acceptance or tie-breaking.

## 8. Error taxonomy

```text
p9.area.invalid-constraint
p9.area.duplicate-space-key
p9.area.request-below-minimum
p9.area.request-above-maximum
p9.area.unallocated-residual
p9.area.integer-overflow-guard
```

Catalog/template defects are distinguished from user request incompatibility in failure metadata.

## 9. Explainability

For diagnostics/UI summary the allocator MAY return:

```text
minimum total
preferred total
maximum total
requested total
per-space min/preferred/fitted/max
phase contributions
```

This data is informational and does not alter ranking semantics.

## 10. NFR

### P9.4-NFR-001

One draft with <= 24 semantic spaces: p99 <= 2 ms.

### P9.4-NFR-002

64 raw drafts: total area fitting p99 <= 40 ms.

### P9.4-NFR-003

Algorithm complexity must be bounded by number of spaces and finite allocation phases, not requested area magnitude one quantum at a time in the common path.

## 11. Acceptance tests

```text
P9.4-AT-001 exact minimum-area request
P9.4-AT-002 exact maximum-area request
P9.4-AT-003 request below minimum rejected
P9.4-AT-004 request above maximum rejected
P9.4-AT-005 remainder distribution deterministic
P9.4-AT-006 permuted input order yields same allocations
P9.4-AT-007 nearFixed bathroom remains near preferred while bedrooms expand
P9.4-AT-008 same inputs repeated 10k times yield same fingerprint
P9.4-AT-009 1..10-room fixture corpus has zero residual for supported requests
P9.4-AT-010 no floating-point value appears in authoritative allocation state
```

## 12. Exit gate

P9.4 is complete when the integer allocator is pure, bounded, exact, deterministic, property-tested across the supported request corpus and exposes typed reasons for infeasible requests.
