# P9.4 — Deterministic Area Fitting v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: `ApartmentTopologyDraft` + template area profile + normalized request  
Produces: `AreaFittedTopologyDraft`

## 1. Objective

Allocate requested **interior** apartment area across interior semantic spaces deterministically, while allocating balcony/loggia/exterior-appendage area from separate template constraints.

The algorithm uses integer units only and must be feasible, explainable and reproducible across supported native platforms.

## 2. Area participation model

P9 v1 request basis is defined by P9.1:

```text
interiorAreaDm2 excludes balcony/loggia/terrace
```

Every template space declares one area participation mode:

```dart
enum SpaceAreaParticipation {
  requestedInteriorArea,
  exteriorAppendage,
}
```

Interior spaces participate in exact requested-area allocation.

Exterior appendages receive independent deterministic target area from their own template min/preferred/max profile and do **not** consume `requestedInteriorAreaDm2`.

## 3. Core data model

```dart
final class SpaceAreaConstraint {
  final String semanticKey;
  final SpaceAreaParticipation participation;
  final int minAreaDm2;
  final int preferredAreaDm2;
  final int maxAreaDm2;
  final int weightBp;
  final bool nearFixed;
}

final class FittedSpaceArea {
  final String semanticKey;
  final SpaceAreaParticipation participation;
  final int areaDm2;
}

final class AreaFittedTopologyDraft {
  final ApartmentTopologyDraft draft;
  final int requestedInteriorAreaDm2;
  final List<FittedSpaceArea> spaces;
  final int allocatedInteriorAreaDm2;
  final int exteriorAppendageAreaDm2;
  final int interiorResidualDm2;
  final String areaFitFingerprint;
}
```

All calculations are integer.

## 4. Functional requirements

### P9.4-FR-001 — Exact interior accounting

For an accepted candidate:

```text
sum(area where participation=requestedInteriorArea)
  == requestedInteriorAreaDm2

interiorResidualDm2 == 0
```

Exterior appendage area is reported separately.

### P9.4-FR-002 — Interior minimums first

Initialize every interior participant to `minAreaDm2`.

If:

```text
sum(interior minimums) > requestedInteriorAreaDm2
```

reject with `p9.area.request-below-minimum`.

### P9.4-FR-003 — Preferred interior allocation phase

Remaining interior area is distributed toward `preferredAreaDm2` using deterministic weighted water-filling.

Priority is explicit `weightBp` plus stable semantic-key tie-break.

### P9.4-FR-004 — Maximum interior expansion phase

After preferred targets, remaining interior area expands spaces toward `maxAreaDm2`.

If:

```text
sum(interior maximums) < requestedInteriorAreaDm2
```

reject with `p9.area.request-above-maximum`.

### P9.4-FR-005 — Near-fixed service spaces

Interior service spaces MAY be `nearFixed`.

They receive allocation up to preferred target before flexible habitable spaces absorb additional area, unless all flexible spaces reach max.

### P9.4-FR-006 — Exterior appendage allocation

For every `exteriorAppendage` space, P9 v1 uses a deterministic template target:

```text
preferredAreaDm2
```

unless a qualified variant seed declares another explicit target within `[min,max]`.

User `interiorAreaDm2` never scales appendage area implicitly.

Future proportional/gross-area behavior requires a new versioned area policy.

### P9.4-FR-007 — Stable remainder allocation

Integer division remainders are assigned in stable order:

```text
higher unmet weighted priority
then semanticKey lexical order
```

No unordered map/set iteration decides remainder ownership.

### P9.4-FR-008 — Area quantum

Default allocation quantum:

```text
1 dm² = 0.01 m² = 10,000 mm²
```

P9.6 geometry uses a `10 mm` coordinate grid and may realize target area within its explicit geometric tolerance.

## 5. Deterministic interior algorithm

```text
INPUT requestedInteriorArea, interiorConstraints[]

1 validate constraints
2 allocate every interior space = min
3 remaining = requested - sum(min)
4 phase A: distribute toward preferred
5 phase B: distribute toward max
6 deterministic integer remainder distribution
7 if remaining != 0 -> reject
8 allocate appendage spaces independently from template targets
9 emit ordered fitted areas
10 compute areaFitFingerprint
```

Weighted allocation for one phase:

```text
eligible = spaces below phase target
while remaining > 0 and eligible not empty:
  compute unmet capacity
  allocate proportional integer shares by weight
  distribute leftover quanta by stable priority
  remove spaces that hit target
```

If proportional shares all round to zero, deterministic one-quantum progress prevents a loop.

## 6. Constraint validation

For each space:

```text
min > 0
min <= preferred <= max
weightBp > 0 when participation=requestedInteriorArea
```

For exterior appendages, weight may be ignored by v1 policy but remains valid metadata for future area policies.

For template:

```text
semantic keys unique
interior min/max envelope feasible
appendage target within min/max
integer totals within safe range
```

## 7. Fingerprint

`areaFitFingerprint` includes:

```text
draftFingerprint
requestedInteriorAreaDm2
areaPolicyVersion
for each semantic key in stable order:
  participation
  allocatedAreaDm2
allocatorVersion
```

Any change that can alter allocation for unchanged inputs requires version bump.

## 8. Invariants

### P9.4-INV-001

Every accepted fitted space satisfies:

```text
min <= fitted <= max
```

### P9.4-INV-002

Total interior-participating area equals requested interior area exactly.

### P9.4-INV-003

Balcony/loggia/terrace area does not reduce or inflate `allocatedInteriorAreaDm2`.

### P9.4-INV-004

Same ordered or permuted constraints yield the same semantic allocation after canonical sorting.

### P9.4-INV-005

No floating-point arithmetic controls acceptance/tie-breaking.

### P9.4-INV-006

Changing balcony preferred area without changing interior request cannot change interior-space allocation.

## 9. Error taxonomy

```text
p9.area.invalid-constraint
p9.area.duplicate-space-key
p9.area.invalid-participation
p9.area.request-below-minimum
p9.area.request-above-maximum
p9.area.appendage-target-out-of-range
p9.area.unallocated-residual
p9.area.integer-overflow-guard
```

Catalog/template defects are distinguished from user request incompatibility in structured facts.

## 10. Explainability

Diagnostic summary MAY expose:

```text
requested interior total
interior min/preferred/max totals
allocated interior total
exterior appendage total
per-space participation + min/preferred/fitted/max
phase contributions
```

Candidate cards SHOULD display interior area and appendage area separately where appendages exist.

## 11. NFR

### P9.4-NFR-001

One draft with <= 24 semantic spaces: p99 <= 2 ms.

### P9.4-NFR-002

64 raw drafts total area fitting: p99 <= 40 ms.

### P9.4-NFR-003

Complexity bounded by number of spaces and finite phases, not requested area magnitude one quantum at a time in common path.

## 12. Acceptance tests

```text
P9.4-AT-001 exact interior minimum request
P9.4-AT-002 exact interior maximum request
P9.4-AT-003 request below interior minimum rejected
P9.4-AT-004 request above interior maximum rejected
P9.4-AT-005 remainder distribution deterministic
P9.4-AT-006 permuted input order yields same allocations
P9.4-AT-007 nearFixed bathroom stays near preferred while bedrooms expand
P9.4-AT-008 balcony area allocated separately and does not consume interior request
P9.4-AT-009 changing balcony preferred area leaves interior allocation unchanged
P9.4-AT-010 same inputs repeated 10k times yield same fingerprint
P9.4-AT-011 1..10-room supported corpus has zero interior residual
P9.4-AT-012 no floating-point value appears in authoritative allocation state
```

## 13. Exit gate

P9.4 is complete when the allocator is pure, bounded, exact for requested interior area, explicit about appendage area, deterministic under source-order permutations, property-tested across the supported corpus and exposes typed reasons for infeasible requests.
