# P9.9 — ApartmentWizardProvider v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: P9.1..P9.8 services  
Integrates with: accepted P8 `WizardProviderRegistry`, `WizardSession`, reserved mutation lifecycle

## 1. Objective

Provide the production P9 adapter that exposes Apartment generation through the existing P8 Wizard without adding a second transaction engine or state authority.

P9.9 owns orchestration and state transitions, not core topology algorithms.

## 2. Two-phase apartment flow

Apartment generation has two distinct phases:

```text
A. exploration
   request -> candidate set -> card selection

B. commit preparation
   exact selected candidate -> reserved P8 preview/diff/apply
```

Exploration allocates no canonical entity IDs and mutates no canonical project state.

## 3. Provider/session model

Because P8 `WizardProvider.generate()` receives one typed parameter object, the P9 parameter object used by the provider MUST carry selection explicitly without mixing it into normalized user intent.

Recommended shape:

```dart
final class ApartmentWizardParameters extends WizardParameters {
  final ApartmentRequestInput request;
  final ApartmentCandidateSelection? selection;
}

final class ApartmentCandidateSelection {
  final String candidateFingerprint;
  final String templateIdValue;
  final int templateVersion;
  final String variantSeedId;
}
```

`request` normalizes to `NormalizedApartmentRequest` and `intentFingerprint`.

`selection` is session state:

- excluded from request intent fingerprint;
- required only before P8 preview generation;
- invalidated whenever any request field changes;
- resolved against the current generated candidate set by exact fingerprint.

## 4. Wizard family descriptor

Recommended descriptor:

```text
familyId            apartment
displayNameKey      wizard.family.apartment
templateId          stable P9 provider template identity
templateVersion     provider contract version
generatorVersion    explicit P9 generator version
supportedScopes     { level }
```

Production UI gets availability from `WizardProviderRegistry`; it does not hard-code the Apartment button as always enabled.

## 5. Target policy v1

### P9.9-FR-001

P9 v1 supports `LevelWizardTarget` only.

### P9.9-FR-002

The target Level MUST:

- exist in current canonical aggregate;
- belong to the target BuildingId;
- contain no canonical Spaces;
- contain no StructuralZones that would conflict with apartment ownership;
- remain at the same `LocalProjectVersion` used to prepare preview.

The empty-level restriction is deliberate P9 scope. Multi-apartment floor packing belongs to P10.

## 6. Exploration orchestration

Conceptual application service:

```dart
final class ApartmentCandidateSetService {
  ApartmentCandidateSet generate({
    required ApartmentRequestInput input,
    required LevelWizardTarget target,
    required ProjectAggregateRoot project,
  });
}
```

Pipeline:

```text
normalize P9.1
-> catalog filter P9.2
-> grammar P9.3
-> area fit P9.4
-> semantic validation P9.5
-> geometry P9.6
-> score/diversify P9.7
-> vector scenes P9.8
```

Output is immutable and has a `candidateSetFingerprint`.

## 7. Candidate set contract

```dart
final class ApartmentCandidateSet {
  final NormalizedApartmentRequest request;
  final String candidateSetFingerprint;
  final List<RankedApartmentCandidate> candidates;
  final List<P9Failure> rejectedSummary;
}
```

Normally returns 3..6 candidates; fewer is allowed when quality/compatibility limits are explicit.

## 8. Selection lifecycle

### P9.9-INV-001

Selection always refers to an exact `candidateFingerprint` present in the current candidate set.

### P9.9-INV-002

Changing any semantic request field clears selection and candidate set.

### P9.9-INV-003

Changing only UI presentation state (expanded details, hover, theme, responsive width class, orientation, preview zoom/pan) does not clear selection.

### P9.9-INV-004

Selection itself does not reserve canonical IDs.

## 9. P8 generate adapter

When `WizardProvider.generate()` is called:

```text
1 validate target
2 normalize request
3 regenerate candidate set deterministically OR use an immutable session snapshot verified by fingerprint
4 find exact selected candidateFingerprint
5 if absent -> fail closed
6 create ApartmentReservedProjectCommand from exact selected candidate semantic payload
7 return command to P8 reserved coordinator
```

If deterministic regeneration is used in step 3, exact candidate fingerprint equality is mandatory before preview. The provider may not silently substitute the new top-ranked candidate.

Recommended implementation is to carry an immutable selected-candidate snapshot within the application Wizard session and verify its request/catalog/generator fingerprints before command construction.

## 10. No hidden provider state

### P9.9-INV-005

`ApartmentWizardProvider` itself is stateless/reentrant. It MUST NOT retain “last selection” in a mutable singleton field.

Session-specific state belongs to the P8/P9 Wizard session model.

## 11. Validation stages

Provider validation returns structured issues:

```text
parameter blockers       P9.1
no compatible templates  P9.2
no valid candidates      P9.3..P9.7
target not empty         P9.9
selection missing        P9.9
selection stale          P9.9
```

Only after all blockers are clear may Preview be enabled.

## 13. Staleness dimensions

A selection becomes stale if any changes:

```text
request.intentFingerprint
catalogVersion
templateVersion
generatorVersion
scoringProfileVersion
candidate geometryFingerprint
LocalProjectVersion when entering reserved preview
```

Candidate-card browsing itself does not bind `LocalProjectVersion` permanently; P8 preview does.

Responsive layout, orientation, input modality, theme, text scale and viewport state do NOT make a candidate stale.

## 14. Semantic UX state machine

The Wizard owns one platform-neutral semantic state machine:

```text
editingParameters
  -> generating
  -> candidatesReady
  -> candidateSelected
  -> preparingPreview
  -> previewReady
  -> applying
  -> completed
```

Failure substates return to the nearest recoverable state with user input preserved.

Cancel before Apply leaves canonical fingerprint/version/Undo unchanged.

This state machine is authoritative whether the UI renders it as desktop panes, tablet split view or phone routes.

## 15. Responsive presentation shell

P9.9 follows `02-p9-cross-platform-responsive-input-contract-v2.md`.

The provider/session MUST NOT encode desktop/tablet/phone branching.

Presentation adapter derives from `ElecXPresentationCapabilities` and maps the same session into:

```text
COMPACT
  one semantic step/surface at a time
  candidate carousel / single-card review
  sticky primary actions

MEDIUM
  parameters + candidates or two-column candidate region
  details sheet/panel

EXPANDED
  parameters + candidate grid + selected details/preview

LARGE
  persistent multi-pane workspace where useful
```

### P9.9-INV-006

Crossing responsive breakpoints preserves the same Wizard session object/state and candidate fingerprints.

### P9.9-INV-007

No candidate generation request is triggered solely by layout-class/orientation/window-size change.

## 16. Semantic navigation contract

The semantic navigation model is:

```text
parameters
candidates
candidateDetails
preview
completed
```

Presentation MAY express this as:

```text
pages
panes
tabs
bottom sheets
side sheets
```

but the semantic step remains independent of widget hierarchy.

System/mobile Back maps to semantic Back.

Back preserves valid request/candidate state; it is not equivalent to Cancel/Discard.

## 17. Input operation mapping

The provider/presentation boundary exposes semantic operations rather than modality-specific mutations.

Required operations include:

```text
generate
selectCandidate
nextCandidate
previousCandidate
openCandidateDetails
openPreview
openDiff
apply
cancel
back
```

Input adapters map:

```text
mouse click / keyboard Enter / touch tap / stylus tap
        -> same selectCandidate operation
```

No required operation may be hover-only, right-click-only or long-press-only.

## 18. Generate concurrency / cancellation

### P9.9-FR-003

At most one authoritative candidate generation is active per Wizard session/request revision.

Repeated Generate activation while the same request is already running MUST be deduplicated/disabled.

### P9.9-FR-004

If user changes semantic request while generation is in flight:

```text
old result becomes obsolete
new request revision is authoritative
late old result must not replace newer state
```

An incrementing session request revision or equivalent token SHOULD enforce this.

### P9.9-FR-005

Transient generation cancellation mutates no canonical project state.

## 19. Lifecycle / resize preservation

Within a live app session, these transitions preserve recoverable Wizard state:

```text
portrait <-> landscape
window resize
responsive class change
tablet split-screen resize
app temporary background/foreground where framework state remains alive
keyboard attach/detach
mouse attach/detach
```

They MUST NOT allocate a new candidate selection or reset user parameters.

## 20. Localization/a11y

Provider emits stable message/field keys and structured facts. UI owns RU/EN strings.

Candidate cards are keyboard/selectable controls with >=48dp touch targets and concise screen-reader semantic summary from P9.8.

Focus order follows task order even if responsive panes visually rearrange.

## 21. NFR

### P9.9-NFR-001

Exploration pipeline hard thresholds are defined in P9.13; provider orchestration overhead itself SHOULD be < 20 ms p99 excluding generation/render stages.

### P9.9-NFR-002

No network/backend requirement.

### P9.9-NFR-003

Provider is safe to invoke repeatedly and has no global mutable session state.

### P9.9-NFR-004

Responsive relayout/orientation change must complete without rerunning the candidate pipeline when semantic request is unchanged.

## 23. Exit gate

P9.9 is complete when Apartment is a real P8 provider with explicit Level targeting, immutable candidate exploration, exact selection identity, no hidden state, fail-closed staleness, zero canonical mutation before P8 Apply, one semantic Wizard state machine across responsive shells, modality-independent operations, and state preservation across resize/orientation/input-capability changes.
