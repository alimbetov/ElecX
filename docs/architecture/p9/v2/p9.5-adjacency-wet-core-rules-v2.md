# P9.5 — Adjacency & Wet-Core Rules v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: `AreaFittedTopologyDraft`  
Produces: validated semantic topology or typed rejection

## 1. Objective

Define explicit, machine-checkable apartment adjacency, circulation, privacy and wet-core constraints before geometry is accepted.

P9.5 prevents semantically incoherent candidates from reaching scoring or canonical materialization.

## 2. Rule classes

```dart
enum TopologyRuleStrength { required, preferred, forbidden }

enum AdjacencyRelation {
  directBoundary,
  directAccess,
  openConnection,
  sameWetCore,
  exteriorExposure,
  reachableWithoutPrivateTransit,
}
```

Rules are typed and conditionally active by normalized request/template.

## 3. Graphs

P9.5 evaluates three related graphs:

```text
A. semantic adjacency graph
   which spaces should/must share a relation

B. access/circulation graph
   which spaces are traversable from entry

C. wet-core grouping graph
   which service spaces belong to the same compact service cluster
```

These graphs MUST NOT be conflated into one generic edge kind.

## 4. Required base rules

### P9.5-FR-001 — Entry reachability

Every occupied/habitable/service space except balcony/loggia MUST be reachable from the apartment entry through allowed access edges.

No disconnected island is accepted.

### P9.5-FR-002 — Private-room transit prohibition

A bedroom MUST NOT be the only transit path to another bedroom, bathroom, kitchen, entry or general circulation space.

### P9.5-FR-003 — Bathroom privacy

Bathroom/WC direct access from a bedroom MAY be allowed only when the template explicitly models an ensuite role. Otherwise access must originate from circulation/day distribution.

### P9.5-FR-004 — Kitchen modes

```text
separate       -> kitchen is a distinct SpaceUsage.kitchen
kitchenLiving  -> one SpaceUsage.kitchenLiving
openPlan       -> explicit open connection/day-zone semantic contract
```

The validator MUST reject a draft that implements the wrong semantic mode even if geometry could fit.

### P9.5-FR-005 — Balcony/loggia attachment

Every balcony/loggia requires exactly one declared primary attachment to an exterior-facing habitable/day space unless the template explicitly supports multiple access.

A balcony cannot attach only to corridor/service space in v1.

### P9.5-FR-006 — Wet-core membership

Wet spaces:

```text
kitchen / kitchenLiving wet side
bathroom
wc
showerRoom
laundry when present
```

are assigned to one or more explicit `WetCoreGroup`s.

A template defines maximum number of wet-core groups and which semantic roles may bridge groups.

### P9.5-FR-007 — Wet-core compactness precondition

Before geometry, the semantic topology must make compact wet grouping possible. A wet-core rule MUST NOT require mutually unreachable/contradictory placement anchors.

Geometric compactness is checked again after P9.6.

### P9.5-FR-008 — Exterior exposure

Spaces declared `requiresExteriorExposure=true` must have an exterior-exposure intent. Final boundary realization is validated in P9.6.

Bedrooms and living/day spaces normally require exterior exposure in catalog-qualified v1 templates; corridor, WC and storage do not unless template says otherwise.

## 5. Rule model

```dart
final class TopologyAdjacencyRule {
  final String ruleId;
  final TopologyRuleStrength strength;
  final SemanticSpaceSelector left;
  final SemanticSpaceSelector right;
  final AdjacencyRelation relation;
  final GrammarCondition? when;
  final int preferredPenaltyBp;
}
```

`ruleId` is stable inside `templateVersion` and appears in diagnostics.

## 6. Required/preferred/forbidden semantics

### required

Failure rejects candidate.

### forbidden

Presence rejects candidate.

### preferred

Failure does not reject. It produces a typed quality penalty consumed by P9.7.

Preferred penalties are bounded and versioned; P9.5 does not itself compute the final score.

## 8. Wet-core policies

Conceptual:

```dart
final class WetCorePolicy {
  final int minGroupCount;
  final int maxGroupCount;
  final Set<SpaceUsage> wetUsages;
  final Set<WetCoreRelation> requiredRelations;
  final Set<WetCoreRelation> preferredRelations;
}
```

Example v1 policies:

```text
compactSingleCore
  max groups = 1
  bathroom/wc/kitchen wet anchor grouped

splitDualCore
  max groups = 2
  allowed for large/split-day-night templates
```

No template may silently create an unbounded number of wet clusters.

## 9. Semantic validation pipeline

```text
1 resolve active rules
2 verify referenced semantic keys/roles
3 build adjacency graph
4 build access graph
5 entry reachability
6 private-transit checks
7 required rules
8 forbidden rules
9 wet-core grouping feasibility
10 exterior-exposure intent checks
11 collect preferred misses
12 emit semantic validation report
```

## 11. Invariants

### P9.5-INV-001

Every required rule is either satisfied or candidate is rejected.

### P9.5-INV-002

No forbidden relation exists in an accepted candidate.

### P9.5-INV-003

Every accepted non-balcony space is reachable from entry.

### P9.5-INV-004

Private-room transit violations are zero for accepted v1 candidates.

### P9.5-INV-005

Preferred misses never mutate topology to hide the miss.

### P9.5-INV-006

Rule evaluation order cannot change acceptance or metrics.
