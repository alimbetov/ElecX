# P9 Associative / Parametric Geometry Editing — Forward Contract v2

Status: **NORMATIVE FORWARD CONTRACT**  
Scope: P7 stable boundaries → P9 generated apartment materialization → P13/P14 CAD interaction → P15 selective regeneration  
Roadmap note: this document **does not create a new P9.14 stage**. It constrains existing P7/P9.11/P9.12/P13/P14/P15 implementation so generated geometry remains editable rather than becoming a one-shot artifact.

---

## 1. Objective

Every apartment generated by P9 MUST become ordinary editable canonical ElecX geometry after Apply.

A generated room is not a frozen image or immutable result. After materialization the user must be able to change:

```text
room width / length through boundary displacement
wall/boundary position
wall thickness through an explicit wall assembly model
hosted openings and future engineering objects
```

and ElecX must deterministically propagate the edit through coupled neighboring geometry according to an explicit propagation policy.

Core principle:

```text
GENERATED GEOMETRY
      ↓ Apply
CANONICAL EDITABLE GEOMETRY
      ↓ manual command
CONSTRAINT / PROPAGATION SOLVER
      ↓
VALIDATED CANDIDATE
      ↓ Preview/Diff
ATOMIC COMMIT
```

There is no separate immutable "wizard geometry" after P9.11 commit.

---

## 2. Why this contract exists

Without associative editing, a generated apartment would degrade into unrelated polygons after the first manual resize. That would break:

- stable wall/edge hosting;
- openings and electrical-device attachment;
- future route anchors;
- undo/redo quality;
- P15 selective regeneration;
- P10 multi-apartment composition;
- P13 auto-placement;
- P14 professional CAD editing.

This contract therefore defines the minimum semantic structure that P9 materialization must preserve even before the full editing solver is implemented.

## 3. Authoritative geometry operation

### 3.1 Boundary displacement is primary

The canonical edit primitive is **boundary displacement**, not direct replacement of room width/height fields.

Conceptual command:

```dart
final class MoveBoundaryCommand implements ProjectCommand {
  final BoundaryEdgeId boundaryEdgeId;
  final int deltaMm;
  final BoundaryMoveAxis axis;
  final GeometryPropagationMode propagationMode;
  final BoundaryMoveAnchor anchor;
}
```

A UI operation such as:

```text
Living width: 5000 mm -> 5500 mm
```

is a presentation-level convenience that resolves to a boundary displacement:

```text
Move east boundary +500 mm
```

Room width/length remain derived geometric properties unless a future parametric schema explicitly promotes them to independent constraints.

### 3.2 No direct widget mutation

Forbidden:

```text
Flutter widget/controller
  -> mutate room polygon
  -> mutate neighbor polygon
  -> save
```

Required:

```text
UI intent
  -> semantic geometry edit command
  -> propagation candidate
  -> validation
  -> Preview/Diff where required
  -> one canonical ProjectChangeSet
```

## 4. Topology-preserving vs topology-changing edits

### 4.1 Topology-preserving edit

Examples:

```text
translate wall without adding/removing vertices
resize rectangular room by moving one existing boundary
translate a coupled downstream room chain
change wall thickness while preserving faces/hosts
```

For topology-preserving edits, durable identity SHOULD remain stable:

```text
BoundaryEdgeId W17 before
BoundaryEdgeId W17 after
```

P7 lineage is:

```text
preserved(W17)
```

### 4.2 Topology-changing edit

Examples:

```text
split wall
merge collinear wall segments
introduce/remove recess
merge rooms
split room
remove boundary
```

These MUST use P7 `BoundaryEdgeLineage`:

```text
preserved
split
merged
created
removed
```

No downstream host may infer replacement identity from list index or geometric proximity alone.

## 5. Shared-boundary coupling

P9/P7 MUST represent enough canonical information to know that two room faces describe one shared physical relationship.

Conceptual contract:

```dart
final class SharedBoundaryConstraint {
  final SharedBoundaryConstraintId id;
  final SpaceId firstSpaceId;
  final BoundaryEdgeId firstEdgeId;
  final SpaceId secondSpaceId;
  final BoundaryEdgeId secondEdgeId;
  final BoundaryCouplingMode mode;
}

enum BoundaryCouplingMode {
  coincident,
  separatedByWallAssembly,
}
```

Required invariants:

```text
one coupled relation references existing stable BoundaryEdgeId values
coupled geometry has deterministic orientation/normal semantics
one edge cannot silently belong to incompatible couplings
constraint graph is persisted as canonical/project-derived state, not UI cache
```

P9.11 may materialize this relation directly or through an equivalent existing canonical adjacency/wall-host structure, but the relation MUST be recoverable without geometric guessing.

## 6. Geometry propagation modes

Initial product contract defines three modes.

### 6.1 `pushChain`

The driven boundary moves by `deltaMm`. Downstream coupled spaces translate in the propagation direction while preserving their dimensions where possible.

Example:

```text
A | B | C | D

move A/B boundary +500 mm east

A grows +500
B translates +500
C translates +500
D translates +500
```

This mode may expand the containing envelope when the final downstream boundary is not locked.

### 6.2 `resizeNeighbor`

The driven boundary moves but the opposite/downstream envelope remains fixed.

Example:

```text
A | B

shared wall +500 mm east

A width +500
B width -500
outer envelope unchanged
```

The operation fails closed if the dependent room would violate min dimension/area/aspect or other active constraints.

### 6.3 `pushUntilLock`

Propagation translates dependent geometry until a locked boundary/constraint is reached.

If the requested displacement cannot be satisfied without violating the lock:

```text
REJECT
```

The solver MUST NOT silently switch to shrinking another room.

Diagnostic example:

```text
Cannot move boundary +500 mm.
Propagation reached locked structural boundary W-104.
Affected path:
Living -> Kitchen -> Corridor -> W-104
```

## 7. Constraint graph and propagation solver

The future solver operates on an explicit graph, not arbitrary polygon scanning.

Conceptually:

```text
GeometryConstraintGraph
├── BoundaryNode
├── SpaceNode
├── SharedBoundaryConstraint
├── WallAssemblyConstraint
├── HostConstraint
├── LockConstraint
└── EnvelopeConstraint
```

A boundary move creates a deterministic propagation frontier:

```text
driven boundary
    ↓
shared/coupled face
    ↓
dependent space
    ↓
opposite dependent boundary
    ↓
next coupled space
```

Hard requirements:

- bounded traversal;
- deterministic ordering;
- cycle detection;
- no dependency on Flutter/display order;
- integer-mm authoritative geometry;
- no floating-point value controls acceptance/tie-break;
- fail closed on contradictory constraints.

---

## 8. Locks and anchors

Future canonical geometry editing supports explicit locks/anchors.

Minimum concepts:

```text
boundary locked in world position
space locked against translation
space locked against resize
outer envelope locked
structural wall locked
hosted engineering object locked from automatic relocation
```

Locks are semantic constraints, not disabled UI controls.

A command encountering a lock returns a typed conflict explaining the propagation path that reached it.

## 9. Wall thickness model

### 9.1 Thickness MUST NOT be duplicated per room edge

Current P7 `ProjectBoundaryEdge` represents one logical boundary edge with `start/end` geometry and stable identity. Wall thickness MUST NOT be added independently to both adjacent room edges because that permits inconsistent values for one physical wall.

### 9.2 Wall assembly

Introduce/reuse a physical wall assembly entity conceptually equivalent to:

```dart
final class WallAssembly {
  final WallAssemblyId id;
  final BoundaryEdgeId firstFaceEdgeId;
  final BoundaryEdgeId? secondFaceEdgeId;
  final int thicknessMm;
  final WallReferenceMode referenceMode;
  final ConstructionId? constructionId;
}
```

For exterior/single-face boundaries, `secondFaceEdgeId` may be absent according to the final wall model.

### 9.3 Thickness anchor

Changing wall thickness requires an explicit anchor:

```dart
enum WallThicknessAnchor {
  firstFace,
  centerline,
  secondFace,
}
```

Examples:

```text
firstFace
  first face stays fixed
  second face moves by +delta thickness
  dependent geometry on second side propagates

secondFace
  symmetric inverse

centerline
  both faces move by delta/2 according to integer-mm rounding contract
```

No wall-thickness change may silently decide which room loses/gains area.

## 10. Hosted openings and engineering objects

A host follows durable identity, not absolute pixel coordinates.

Conceptual host placement:

```dart
final class BoundaryHostPlacement {
  final BoundaryEdgeId hostEdgeId;
  final int offsetAlongEdgeMm;
  final int offsetNormalMm;
}
```

When a topology-preserving boundary moves:

```text
wall W17 moves +500 mm
Door D12 hosted on W17 -> moves with W17
Socket S31 hosted on W17 -> moves with W17
Switch SW4 hosted on W17 -> moves with W17
```

Relative offset along the preserved edge remains stable unless the host has its own constraint/lock.

When an edge splits/merges, existing P7 host-remap/lineage logic determines whether the host is preserved, requires geometric remap, or becomes invalid.

P9.11 mandatory openings MUST be materialized in a form compatible with this contract from day one.

## 11. Future engineering-route interaction

Boundary movement may invalidate engineering routes without deleting them silently.

Required future state transition:

```text
boundary moved
  ↓
hosted device moved
  ↓
route anchor changed
  ↓
route state = needsReconciliation | needsReroute | valid
```

P13/P14 may automatically reconcile simple cases, but authoritative engineering connectivity is never mutated implicitly by presentation code.

## 12. Candidate-based manual editing

Manual geometry edits follow the same safety model as Wizard Apply.

```text
current canonical project
    ↓
manual geometry edit command
    ↓
transient candidate
    ↓
constraint propagation
    ↓
aggregate + geometry validation
    ↓
Preview/Diff when material
    ↓
atomic commit
```

One confirmed operation produces:

```text
1 ProjectChangeSet
1 LocalProjectVersion increment
1 UndoRecord
```

Pointer move/drag during interaction remains transient and MUST NOT create repeated canonical mutations.


## 14. Provenance and P15 selective regeneration

### 14.1 User-driven vs propagated changes

A manual edit that drives propagation MUST NOT mark every translated dependent entity as an independent user override.

Conceptual provenance:

```dart
final class GeometryEditProvenance {
  final GeometryEditOperationId operationId;
  final BoundaryEdgeId driverBoundaryEdgeId;
  final int deltaMm;
  final GeometryPropagationMode mode;
  final Set<EntityId> userDrivenEntities;
  final Set<EntityId> propagatedEntities;
}
```

P9.12/P15 should preserve the **driver constraint** and distinguish propagated effects.

Example:

```text
USER OVERRIDE
Living east boundary +500 mm

PROPAGATED
Kitchen translated +500 mm
Corridor translated +500 mm
Bathroom translated +500 mm
```

The propagated positions are not four independent manual decisions.

### 14.2 Field-aware provenance

Manual boundary editing marks relevant generated properties such as:

```text
geometry
boundaryPosition
wallAssemblyThickness
```

as overridden at the correct semantic owner.

P15 regeneration later replays/reconciles user-driven constraints against the new generated baseline rather than blindly persisting old world coordinates.

## 21. Architectural invariants

### AE-INV-001

Generated P9 geometry is ordinary editable canonical geometry after Apply.

### AE-INV-002

A topology-preserving move preserves durable boundary identity whenever the same logical edge continues to exist.

### AE-INV-003

Propagation is explicit, deterministic and bounded; hidden arbitrary room shrink/grow is forbidden.

### AE-INV-004

Wall thickness is owned by a physical wall/assembly concept, not duplicated independently on adjacent room edges.

### AE-INV-005

Hosted objects follow stable hosts; they are not reattached by list index or screen proximity.

### AE-INV-006

Manual geometry editing uses candidate validation and atomic command semantics.

### AE-INV-007

User-driven geometry constraints and solver-propagated consequences are distinguishable in provenance.

### AE-INV-008

No desktop/tablet/mobile presentation path may bypass the same canonical propagation/validation engine.

### AE-INV-009

P9 area allocation remains independent from later manual geometry propagation.

### AE-INV-010

P15 regeneration reconciles semantic/manual driver constraints, not stale UI coordinates.
