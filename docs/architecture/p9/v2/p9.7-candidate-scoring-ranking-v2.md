# P9.7 — Candidate Scoring, Ranking & Diversity v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: valid `ApartmentGeometryCandidate[]`  
Produces: ordered `RankedApartmentCandidate[]` (normally 3..6)

## 1. Objective

Rank only valid candidates using deterministic, explainable, versioned quality metrics while preserving useful topology diversity.

Scoring is a product recommendation mechanism. It is **not** normative compliance certification.

## 2. Validity boundary

### P9.7-INV-001

A candidate with any P9.5/P9.6 blocker MUST NOT be scored as selectable.

Pipeline:

```text
validate -> reject blockers -> compute metrics -> score -> diversify -> select top N
```

Never:

```text
score invalid candidate -> let score compensate for violation
```

## 3. Score scale

All metrics and final scores are integer basis points:

```text
0..10000
```

No floating-point comparison controls ordering.

## 4. Scoring profile

```dart
final class ApartmentScoringProfile {
  final String scoringProfileVersion;
  final Map<ApartmentScoreMetric, int> weightBp;
}
```

Weights MUST sum exactly to `10000`.

Recommended v1 profile:

```text
interiorAreaMatch             1600
circulationEfficiency         1400
corridorEfficiency            1000
wetCoreCompactness            1200
roomAspectQuality             1200
privacySeparation             1000
kitchenModeQuality             800
balconyAttachmentQuality       600
familyPreferenceMatch          600
exteriorExposurePreferenceMatch 600
                              -----
                              10000
```

Profile changes that can change ranking require a new `scoringProfileVersion`.

## 5. Metric definitions

### P9.7-FR-001 — interiorAreaMatch

Uses only P9.1 requested interior area and realized interior spaces.

Hard total-area/space limits are already enforced; this metric distinguishes quality among valid candidates based on per-space target deviation and geometric realization tolerance.

Balcony/loggia area is excluded from this metric and evaluated in balcony/appendage quality.

### P9.7-FR-002 — circulationEfficiency

Uses deterministic facts such as:

```text
entry max graph depth
number of circulation transitions
unnecessary branch count
circulation interior-area ratio
```

### P9.7-FR-003 — corridorEfficiency

Penalizes excessive corridor area/length relative to **interior** apartment area while respecting family-qualified target ranges. `corridorSpine` is not penalized merely for having a spine.

### P9.7-FR-004 — wetCoreCompactness

Uses normalized wet-space shared-boundary/distance metrics from P9.6. Hard dispersion violations were already rejected.

### P9.7-FR-005 — roomAspectQuality

Each interior room maps actual aspect ratio/min-dimension quality to `0..10000` relative to template preferred range, then aggregates by stable semantic weights.

### P9.7-FR-006 — privacySeparation

Rewards reduced exposure of bedroom/private paths to entry/day traffic while maintaining valid reachability.

### P9.7-FR-007 — kitchenModeQuality

Requested kitchen semantics already match. This metric rewards topology/geometry quality specific to `separate`, `kitchenLiving` or `openPlan`; it never compensates for semantic mismatch.

### P9.7-FR-008 — balconyAttachmentQuality

Rewards:

```text
valid appendage attachment
adequate attachment boundary length
qualified exterior geometry
preferred host-space relation
appendage area close to template target
```

### P9.7-FR-009 — familyPreferenceMatch

If user supplied `preferredFamily`, a valid candidate in that family receives preference credit. Invalid candidates are never revived by preference.

### P9.7-FR-010 — exteriorExposurePreferenceMatch

Rates candidate-local exposure topology against P9.1 preference:

```text
oneSide
corner
oppositeSides
any
```

This metric MUST NOT claim actual Building facade orientation or cardinal direction compliance.

## 6. Metric normalization

Every metric implementation MUST document:

```text
input facts
best threshold
worst threshold
piecewise/linear mapping
clamping rule
```

Metric functions are pure integer functions.

Example:

```text
corridor ratio <= targetBest -> 10000
ratio >= targetWorst         -> 0
between                       -> integer linear interpolation
```

## 7. Final score

```text
finalScoreBp = sum(metricScoreBp * metricWeightBp) / 10000
```

Integer remainder handling is deterministic. Final score is clamped `0..10000`.

## 8. Score explanation

Every ranked candidate retains:

```dart
final class ApartmentScoreBreakdown {
  final String scoringProfileVersion;
  final Map<ApartmentScoreMetric, int> metricScoreBp;
  final Map<ApartmentScoreMetric, int> weightedContributionBp;
  final int finalScoreBp;
}
```

UI may show simplified localized reasons derived from this typed breakdown.

## 9. Stable tie-break

Equal final scores order by:

```text
1 family stableOrder
2 template stableOrder
3 variant seed stableOrder
4 geometryFingerprint lexical
```

No creation time/random/hash-map order.

## 10. Diversity selection

After full stable ranking, select `3..6` using deterministic diversity rules.

### P9.7-FR-011 — Family diversity first

When quality permits, results SHOULD contain multiple qualified families.

### P9.7-FR-012 — Duplicate suppression

Identical normalized semantic+geometry fingerprints deduplicate; stable highest-ranked instance survives.

### P9.7-FR-013 — Near-duplicate control

`CandidateSimilaritySignature` includes:

```text
family
templateId
space adjacency graph class
wet-core grouping
entry orientation
exterior exposure pattern
mirrored flag
```

A lower-ranked near-duplicate MAY be skipped when materially different valid candidate exists.

### P9.7-FR-014 — Score floor

Diversity must not surface low-quality candidates merely to fill card count.

Recommended v1 selectable floor:

```text
5000/10000
```

Profile-configurable/versioned.

## 11. Candidate count

```text
preferred       4
minimum useful  3
maximum         6
```

If fewer than 3 candidates meet validity/quality floor, return all qualifying candidates plus diagnostic availability metadata; do not fabricate variants.

## 12. Ranking fingerprint

Includes:

```text
scoringProfileVersion
ordered geometryFingerprint + finalScoreBp
selected fingerprints after diversity
```

## 13. Invariants

### P9.7-INV-002

Source collection order cannot change final ordered results.

### P9.7-INV-003

Score explanation contributions reconcile with final score within documented integer rounding.

### P9.7-INV-004

Diversity never advances a lower-scoring candidate except by explicitly excluding a near-duplicate according to versioned policy.

### P9.7-INV-005

User preferences influence quality ranking only; they never bypass hard validation.

### P9.7-INV-006

Exterior appendage area cannot improve `interiorAreaMatch` by inflating the requested interior total.

### P9.7-NFR-002

No locale/rendering/network dependency.

### P9.7-NFR-003

All calculations use bounded integer arithmetic with overflow guards.

## 17. Exit gate

P9.7 is complete when scoring is versioned, integer, explainable and deterministic; interior/appendage/exposure semantics match P9.1/P9.4/P9.6; tie-break/diversity are explicit; invalid candidates cannot enter ranking; and fixture ranking is stable across repeated/platform runs.
