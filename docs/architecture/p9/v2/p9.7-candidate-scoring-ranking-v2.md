# P9.7 — Candidate Scoring, Ranking & Diversity v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: valid `ApartmentGeometryCandidate[]`  
Produces: ordered `RankedApartmentCandidate[]` (normally 3..6)

## 1. Objective

Rank only valid candidates using deterministic, explainable, versioned quality metrics while preserving useful topology diversity.

Scoring is a product recommendation mechanism. It is **not** normative compliance certification.

## 2. Validity boundary

### P9.7-INV-001

A candidate with any P9.5/P9.6 blocker MUST NOT be scored as selectable.

Pipeline is:

```text
validate -> reject blockers -> compute metrics -> score -> diversify -> select top N
```

Never:

```text
score invalid candidate -> let score compensate for violation
```

## 3. Score scale

All metrics and final scores are integer basis points:

```text
0..10000
```

No floating-point comparison controls ordering.

## 4. Scoring profile

```dart
final class ApartmentScoringProfile {
  final String scoringProfileVersion;
  final Map<ApartmentScoreMetric, int> weightBp;
}
```

Weights MUST sum exactly to `10000`.

Recommended v1 profile:

```text
areaMatch                  1600
circulationEfficiency      1400
corridorEfficiency         1000
wetCoreCompactness         1200
roomAspectQuality          1200
privacySeparation          1000
kitchenModeMatch            800
balconyAttachmentQuality    600
familyPreferenceMatch       600
facadePreferenceMatch       600
                           -----
                           10000
```

Profile changes that can change ranking require a new `scoringProfileVersion`.

## 5. Metric definitions

### P9.7-FR-001 — areaMatch

Derived from realized-vs-requested/target areas. Exact requested total and small per-room deviations score highest.

Hard area limits were already enforced; this metric only distinguishes quality among valid candidates.

### P9.7-FR-002 — circulationEfficiency

Uses deterministic metrics such as:

```text
entry max graph depth
number of circulation transitions
unnecessary branch count
circulation area ratio
```

### P9.7-FR-003 — corridorEfficiency

Penalizes excessive corridor area/length relative to apartment area while respecting family intent. A corridorSpine family is not automatically penalized simply for having a spine; scoring uses family-qualified target ranges.

### P9.7-FR-004 — wetCoreCompactness

Uses normalized wet-space shared-boundary/distance metrics from P9.6. Hard dispersion violations were already rejected.

### P9.7-FR-005 — roomAspectQuality

Each room maps actual aspect ratio to a 0..10000 quality score relative to template preferred range, then aggregates using stable semantic weights.

### P9.7-FR-006 — privacySeparation

Rewards reduced access depth exposure of bedrooms/private spaces to entry/day traffic while maintaining valid reachability.

### P9.7-FR-007 — kitchenModeMatch

Requested mode semantics must already match; metric rewards geometry/topology quality specific to that mode, not semantic coercion.

### P9.7-FR-008 — balconyAttachmentQuality

Rewards qualified exterior attachment, adequate boundary length and preferred day/private room attachment declared by template.

### P9.7-FR-009 — familyPreferenceMatch

If user supplied `preferredFamily`, a valid candidate in that family receives a preference bonus metric. Invalid candidates are never revived by this preference.

### P9.7-FR-010 — facadePreferenceMatch

Rates realized exterior exposure against requested facade preference and template intent.

## 6. Metric normalization

Every metric implementation MUST document:

```text
input facts
best threshold
worst threshold
piecewise/linear mapping
clamping rule
```

Metric functions are pure integer functions.

Example:

```text
corridor ratio <= targetBest -> 10000
ratio >= targetWorst         -> 0
between                       -> integer linear interpolation
```

## 7. Final score

```text
finalScoreBp = sum(metricScoreBp * metricWeightBp) / 10000
```

Integer division remainder handling is deterministic. Final score is clamped `0..10000`.

## 8. Score explanation

Every ranked candidate MUST retain:

```dart
final class ApartmentScoreBreakdown {
  final String scoringProfileVersion;
  final Map<ApartmentScoreMetric, int> metricScoreBp;
  final Map<ApartmentScoreMetric, int> weightedContributionBp;
  final int finalScoreBp;
}
```

UI may show simplified reasons such as “compact circulation” or “better day/night separation” derived from this typed breakdown.

## 9. Stable tie-break

When `finalScoreBp` is equal, order by:

```text
1 family stableOrder
2 template stableOrder
3 variant seed stableOrder
4 geometryFingerprint lexical
```

No creation time/random/hash-map order is allowed.

## 10. Diversity selection

Showing six nearly identical mirrors has low product value.

After full stable ranking, select `3..6` using deterministic diversity rules.

### P9.7-FR-011 — Family diversity first

When possible, the first result set SHOULD contain multiple qualified families.

### P9.7-FR-012 — Duplicate suppression

Candidates with identical normalized semantic+geometry fingerprint are duplicates and only the highest-ranked/stable-first survives.

### P9.7-FR-013 — Near-duplicate control

A deterministic `CandidateSimilaritySignature` includes:

```text
family
templateId
space adjacency graph class
wet-core grouping
entry orientation
mirrored flag
```

Selection MAY skip a lower-ranked candidate if its signature is equivalent to an already selected candidate and a materially different valid candidate is available.

### P9.7-FR-014 — Score floor

Diversity must not surface low-quality candidates below a configured minimum score merely to fill N. If only two candidates meet the quality floor, return two and explain reduced availability.

Recommended v1 selectable score floor: `5000/10000`, configurable by profile.

## 11. Candidate count

Target UI count:

```text
preferred  4
minimum useful 3
maximum 6
```

If fewer than 3 valid/quality-floor candidates exist, return all valid candidates plus diagnostic availability metadata; do not fabricate variants.

## 12. Ranking fingerprint

Selection result fingerprint includes:

```text
scoringProfileVersion
ordered candidate geometryFingerprint + finalScoreBp
selected candidate fingerprints after diversity
```

## 13. Invariants

### P9.7-INV-002

Changing source collection order cannot change final ordered results.

### P9.7-INV-003

Score explanation contributions sum consistently with final score within documented integer rounding.

### P9.7-INV-004

Diversity selection never reorders a candidate ahead of a higher-scoring candidate unless the deterministic diversity policy explicitly excludes the near-duplicate.

### P9.7-INV-005

User preferences influence quality ranking only; they cannot bypass hard validation.

## 14. Error codes

```text
p9.score.invalid-profile
p9.score.weight-sum
p9.score.missing-metric
p9.score.invalid-metric-range
p9.score.no-valid-candidates
```

Profile defects are developer configuration failures.

## 15. NFR

### P9.7-NFR-001

Score + rank + diversify 64 candidates p99 <= 25 ms.

### P9.7-NFR-002

No locale/rendering/network dependency.

### P9.7-NFR-003

All calculations use bounded integer arithmetic with overflow guards.

## 16. Acceptance tests

```text
P9.7-AT-001 weights sum to 10000
P9.7-AT-002 invalid candidate cannot be scored selectable
P9.7-AT-003 identical candidates deduplicate
P9.7-AT-004 stable tie-break independent of input order
P9.7-AT-005 preferred family influences valid candidates only
P9.7-AT-006 diversity exposes another family when quality floor permits
P9.7-AT-007 six near-identical mirrors do not fill all cards if alternatives exist
P9.7-AT-008 score breakdown recomputes final score
P9.7-AT-009 repeated ranking yields identical selection fingerprint
P9.7-AT-010 quality floor may return fewer than 3 rather than inventing candidates
```

## 17. Exit gate

P9.7 is complete when scoring is versioned, integer, explainable, deterministic; tie-break/diversity are explicit; invalid candidates cannot enter ranking; and fixture ranking is stable across repeated/platform runs.
