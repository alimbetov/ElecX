# P9.11 — Canonical Spaces / StructuralZone Materialization v2

Status: **READY FOR IMPLEMENTATION**  
Consumes: exact frozen selected candidate + P8 `MutationIdentityReservation`  
Produces: one atomic canonical apartment mutation

## 1. Objective

Materialize the selected apartment candidate into ordinary editable canonical ElecX state:

```text
StructuralZone(kind=apartment)
Spaces(ProjectSpaceType + SpaceUsage)
SpaceBoundaryTopology
ProjectSpaceAdjacencyEntity
ProjectOpeningEntity + stable boundary host where supported/required
Generation provenance (P9.12)
```

Generated state is not a separate “wizard model” after commit.

## 2. Mutation boundary

P9.11 MUST implement one `ReservedProjectCommand` (or equivalent P8 accepted reserved command) whose candidate builder is pure over:

```text
current ProjectAggregateRoot
exact selected ApartmentGeometryCandidate
immutable MutationIdentityReservation
```

One Apply produces:

```text
1 canonical commit
1 LocalProjectVersion increment
1 ProjectChangeSet
1 UndoRecord
```

## 3. Target policy

### P9.11-FR-001

Immediately before candidate construction/commit, revalidate target Level:

```text
Level exists
Level belongs to expected Building
Level contains no Spaces
Level contains no conflicting StructuralZones
current LocalProjectVersion == preview expected version at commit
```

Do not rely only on earlier P9.9 exploration validation.

## 4. Identity reservation plan

Permanent IDs are allocated exactly once when preparing reserved preview.

Required slot classes:

```text
ZoneId                one apartment zone
SpaceId               one per generated semantic space
BoundaryEdgeId        one per canonical boundary segment
SpaceAdjacencyId      one per canonical adjacency entity
OpeningId             one per materialized opening
GenerationId          one generation operation
```

Potential additional IDs are reserved only if current canonical contracts require them.

Slot naming MUST be deterministic from semantic keys:

```text
zone:apartment
space:bedroom:1
space:bathroom:1
edge:bedroom:1:north:0
adj:bedroom:1|corridor:1|sharedBoundary
opening:entry:1
generation:apartment
```

Reservation slot names are not persisted as entity identity but are stable enough for test diagnostics.

### P9.11-INV-002

### P9.11-INV-003

## 6. StructuralZone materialization

Create exactly one apartment StructuralZone in P9 v1:

```text
kind = ProjectStructuralZoneKind.apartment
levelId = target LevelId
spaceIds = all generated interior/balcony spaces owned by apartment
```

Name policy:

- canonical generation MUST be locale-independent;
- default persisted generated name SHOULD be a deterministic neutral value such as `Apartment 1` or a stable project numbering service result;
- RU/EN localized presentation MUST NOT change identity/fingerprint;
- user rename later is ordinary manual mutation/provenance override.

## 7. Space materialization

Each candidate semantic space becomes one `ProjectSpaceEntity`:

```text
id      reserved SpaceId
levelId target LevelId
type    candidate structural type
usage   candidate SpaceUsage
name    deterministic locale-independent generated name
```

Examples:

```text
bedroom:1      -> type room, usage bedroom
kitchen:1      -> type room, usage kitchen
kitchenLiving  -> type room, usage kitchenLiving
corridor:1     -> type corridor, usage corridor
bathroom:1     -> type room, usage bathroom
loggia:1       -> suitable structural type, usage loggia
```

No semantic usage is inferred from `name`.

## 8. Space naming

Generated name ordinal is based on stable semantic key order, never source list order.

Examples of locale-independent canonical fallback names:

```text
Bedroom 1
Bedroom 2
Kitchen
Kitchen-Living
Bathroom 1
WC 1
Corridor
Loggia 1
```

Presentation MAY localize system-generated names using `SpaceUsage + generationKey` until the user explicitly overrides `name`; the stored semantic fingerprint MUST remain locale-independent.

## 9. Boundary topology materialization

P9.6 semantic segments map to reserved P7 identities:

```text
semantic space key
 -> reserved SpaceId
 -> ordered geometry segments
 -> reserved BoundaryEdgeId per segment
 -> ProjectBoundaryEdge
 -> SpaceBoundaryTopology
```

Requirements:

- coordinates exactly match frozen candidate integer-mm geometry;
- ordered loop is continuous/closed;
- every edge belongs to correct SpaceId;
- no `wallIndex` durable identity;
- shared geometric boundaries may be represented by separate per-space edges if P7 ownership requires it, with semantic adjacency connecting spaces.

## 10. Adjacency materialization

P9.5/P9.6 accepted relations become canonical `ProjectSpaceAdjacencyEntity` where the canonical model has a matching semantic relation.

IDs and endpoints use reserved `SpaceId`s.

Endpoint order is normalized by existing canonical adjacency rules.

No adjacency is re-derived from display labels during materialization.

## 11. Openings / entry

Where P9 emits an opening intent and P7 canonical host APIs support the host:

```text
OpeningId -> ProjectOpeningEntity
connected SpaceIds
BoundaryEdgeId host through current stable host registry/adoption contract
```

### P9.11-INV-004

P9 MUST NOT create an opening with ambiguous or numeric-index-only wall hosting.

If mandatory apartment entry cannot be represented with stable hosting in the current canonical model, P9.11 exit gate is blocked; do not create an unhosted fake opening.

Interior door materialization MAY be staged within P9.11, but any omitted physical door must remain an explicit typed deferred opening intent, not silently disappear from semantic access validation.

## 15. Post-commit editability

After commit, normal authoring commands may:

```text

```

P9-specific runtime objects are not required to edit the project.

Provenance handles later regeneration distinction; it does not lock ordinary edits by default.
