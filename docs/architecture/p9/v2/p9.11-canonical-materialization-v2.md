Materialize the selected apartment candidate into ordinary editable canonical ElecX state:

```text
StructuralZone(kind=apartment)
```

## 4. Identity reservation plan

Permanent IDs are allocated exactly once when preparing reserved preview.

Required slot classes:

```text
ZoneId                one apartment zone
SpaceId               one per generated semantic space
BoundaryEdgeId        one per canonical boundary segment
SpaceAdjacencyId      one per canonical adjacency entity
OpeningId             one per canonical access opening
GenerationId          one generation operation
```

Slot naming is deterministic from semantic keys:

```text
zone:apartment
space:bedroom:1
space:bathroom:1
edge:bedroom:1:north:0
adj:bedroom:1|corridor:1|sharedBoundary
opening:entry:1
opening:corridor:1|bedroom:1:door
opening:kitchen:1|livingRoom:1:openPassage
generation:apartment
```

Reservation slot names are diagnostics, not persistent entity identity.

## 6. StructuralZone materialization

Create exactly one apartment StructuralZone in P9 v1:

```text
kind = ProjectStructuralZoneKind.apartment
levelId = target LevelId
spaceIds = all generated interior and exterior-appendage Spaces owned by apartment
```

Canonical generated naming is locale-independent. User rename later is ordinary manual mutation/provenance override.

## 7. Space materialization

Each candidate semantic space becomes one `ProjectSpaceEntity`:

```text
id      reserved SpaceId
levelId target LevelId
type    candidate structural type
usage   candidate SpaceUsage
name    deterministic locale-independent generated fallback
```

Examples:

```text
bedroom:1      -> room + bedroom
kitchen:1      -> room + kitchen
kitchenLiving  -> room + kitchenLiving
corridor:1     -> corridor + corridor
bathroom:1     -> room + bathroom
loggia:1       -> qualified structural type + loggia
```

No semantic usage is inferred from `name`.

## 8. Space naming

Generated ordinal is based on stable semantic-key order.

Locale-independent canonical fallback names MAY be:

```text
Bedroom 1
Bedroom 2
Kitchen
Kitchen-Living
Bathroom 1
WC 1
Corridor
Loggia 1
```

Presentation MAY localize system-generated names from `SpaceUsage + generationKey` until explicit user override. Locale cannot change canonical fingerprint.

## 9. Boundary topology materialization

P9.6 semantic segments map to reserved P7 identities:

```text
semantic space key
 -> reserved SpaceId
 -> ordered integer-mm segments
 -> reserved BoundaryEdgeId per segment
 -> ProjectBoundaryEdge
 -> SpaceBoundaryTopology
```

Requirements:

- exact frozen candidate coordinates;
- continuous closed ordered loop;
- correct SpaceId ownership;
- no durable `wallIndex`;
- interior envelope and exterior appendage boundaries remain semantically distinguishable;
- shared geometric boundaries may use per-space edges if P7 ownership requires it, with canonical adjacency linking Spaces.

## 10. Adjacency materialization

Accepted semantic/geometric relations become canonical `ProjectSpaceAdjacencyEntity` with reserved `SpaceId` endpoints.

Endpoint order follows existing canonical normalization.

No adjacency is re-derived from display labels.

Adjacency alone is **not** sufficient for traversable access; access relations additionally require canonical openings/passages below.

## 11. Mandatory access-opening materialization

### P9.11-FR-002 — Apartment entry

Exactly one primary apartment entry intent from P9.6 MUST materialize as a canonical opening/access entity with a stable `BoundaryEdgeId` host.

### P9.11-FR-003 — Interior access edges

Every P9.5 access edge required for reachability MUST materialize physically as one of:

```text
OpeningKind.door
OpeningKind.openPassage
other explicitly qualified canonical traversable opening kind
```

according to the exact `OpeningIntent` emitted by the selected candidate.

A candidate is not production-complete if its graph says “Bedroom reachable from Corridor” but no canonical traversable opening/pass exists.

### P9.11-FR-004 — Stable hosting

Every wall-hosted opening MUST resolve to a reserved stable `BoundaryEdgeId` using current P7 host registry/adoption contracts.

P9 MUST NOT persist:

```text
wallIndex-only host
ambiguous host
pixel coordinate host
unhosted fake door
```

### P9.11-FR-005 — Opening geometry

Template/candidate opening intent provides at least:

```text
kind
host semantic segment
connected semantic spaces
widthMm
heightMm
baseElevationMm
stable offset/placement rule
```

Opening placement MUST fit the host segment and satisfy current P7 opening profile/host validation.

If the required host cannot represent the opening, that candidate is rejected before Preview/Apply rather than omitting the opening.

### P9.11-INV-004

The canonical access graph induced by materialized openings/open passages MUST preserve P9.5 accepted entry reachability.
