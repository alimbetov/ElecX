# P9.11 — Canonical Spaces / StructuralZone Materialization v1

## Goal

Convert one selected apartment topology candidate into one atomic canonical project mutation using stable reserved identities and the existing P6/P7 domain model.

## Command

```dart
final class ApplyApartmentCandidateCommand implements ReservedProjectCommand {
  final LevelId targetLevelId;
  final ApartmentTopologyCandidate candidate;
  final ApartmentGenerationDescriptor generation;
}
```

The command is immutable after P8 preview preparation.

## v1 target precondition

Target `LevelWizardTarget` must resolve to the expected project/building/level and the Level must be empty of canonical Spaces/StructuralZones for P9 v1.

Fail closed on ownership mismatch, stale target or non-empty level.

## Deterministic reservation slots

Reservation slot names derive from semantic generation keys, for example:

```text
generation
zone:apartment
space:entry
space:living
space:bedroom:1
space:bedroom:2
space:bathroom:1
edge:<space-slot>:<edge-semantic-key>
adjacency:<ordered-slot-pair>
opening:<semantic-opening-key>
```

Slot names are stable semantics; allocated UUID values are not part of generation fingerprints.

## Reserved entities

P9 may reserve:

```text
GenerationId
ZoneId
SpaceId[]
BoundaryEdgeId[]
SpaceAdjacencyId[]
OpeningId[] when generated
```

No ID is allocated in `buildCandidate()`.

## Canonical materialization

One candidate produces:

```text
ProjectStructuralZoneEntity(kind: apartment)
ProjectSpaceEntity[] with typed ProjectSpaceType + SpaceUsage
SpaceBoundaryTopology for every generated space
ProjectSpaceAdjacencyEntity[]
ProjectOpeningEntity[] when supported
updated ProjectLevelEntity zoneIds/spaceIds
GenerationState/provenance metadata from P9.12
```

All references use stable typed IDs.

## Area/name rules

Space display names are generated deterministically from semantic role and ordinal but are not used as identity. Example defaults may be localized at presentation time or stored as stable project display strings according to existing project naming conventions; behavior never infers semantics back from the name.

## Boundary mapping

P9.6 normalized polygon edges are mapped to reservation slots by semantic edge key. `BoundaryEdgeId` is created exactly once by reservation and reused for preview/commit.

## Adjacency materialization

Only validated semantic/physical adjacencies are committed. Endpoint order uses the canonical `ProjectSpaceAdjacencyEntity` normalization already present in the domain.

## Candidate validation

Before commit candidate publication:

```text
ProjectAggregateValidator
CandidateGraphValidator / mutation validation
P9-specific provenance validation
```

must all pass.

## Atomicity

Any failure before commit leaves the previous aggregate unchanged. Successful generation creates:

```text
exactly 1 ProjectChangeSet
exactly 1 LocalProjectVersion increment
exactly 1 UndoRecord
```

Undo removes the entire generated apartment atomically. Redo restores the same canonical IDs and semantic fingerprint.

## Editable result

After commit, generated entities are ordinary canonical structures. Existing authoring commands can later rename/reclassify/edit/split/merge spaces subject to their normal invariants. P9 must not require a special generated-apartment editor.

## Exit gate P9-G11

```text
all permanent IDs reserved once
zone/spaces/boundaries/adjacency canonical
one Apply = one change set/version/undo
Undo/Redo preserves exact IDs
aggregate validators pass
failed materialization leaves fingerprint unchanged
committed result editable through normal canonical commands
```
