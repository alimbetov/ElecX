# Project Template Wizard v1

## Status

Implementation specification for the native-only ElecX project/template generation wizard.

This specification is subordinate to:

- `docs/architecture/native-project-portability-and-sync.md`
- `docs/architecture/project-composition-foundation-decisions-v1.md`
- `docs/architecture/project-structure-authoring-v1.md`

If requirements conflict, the foundation decisions and native portability baseline win.

## Platform scope

Supported native targets:

```text
macOS
Windows
Linux
Android
iOS
iPadOS
```

Web/browser runtime, browser persistence and browser-specific project semantics are out of scope.

## Product objective

The Wizard is an authoring accelerator that creates canonical ElecX project candidates from deterministic templates.

It is not:

- a second project model;
- a second persistence format;
- a widget-side graph builder;
- a backend-dependent generation service;
- a platform-specific project type.

Generated projects immediately become ordinary editable ElecX projects.

## Primary UX

```text
Project Hub / New Project
[ Blank ] [ Demo ] [ Wizard ]
```

The editor may additionally expose:

```text
[ + Building ]
[ + Level ] [ + Room ]
[ Wizard ]
```

The Wizard always receives an explicit insertion/creation context. It never infers a target Building/Level from stale widget state.

## Wizard families

Initial families:

```text
Apartment
Cottage / detached house
Building
Residential complex
```

Later families may be added without changing the canonical project schema.

## Typed configuration contracts

Production contracts must not use an untyped `Map<String, Object?>` as the authoritative Wizard parameter API.

Target shape:

```dart
sealed class WizardParameters {}

final class ApartmentWizardParameters extends WizardParameters {}
final class CottageWizardParameters extends WizardParameters {}
final class BuildingWizardParameters extends WizardParameters {}
final class ResidentialComplexWizardParameters extends WizardParameters {}
```

Template definitions are typed and versioned:

```dart
final class TemplateDefinition<P extends WizardParameters> {
  final TemplateId templateId;
  final int templateVersion;
  final GeneratorVersion generatorVersion;
  final TemplateFamily family;
  final String displayName;
  final P Function() defaults;
  final TemplateConstraintSet<P> constraints;
}
```

Exact Dart syntax may differ, but compile-time configuration types are required at the application/domain boundary.

## Apartment generator

Supported conventional habitable-room range:

```text
1..10
```

Service spaces are separate from `roomCount`.

Minimum typed inputs include:

```text
roomCount
approximateAreaM2
shape/aspect ratio
entry side
facade/window sides
topology family
kitchen mode
bathroom mode
balcony/loggia mode
```

Topology families include common design patterns such as:

```text
compact
linear
corridor
centralHall
corner
dualAspect
splitDayNight
openPlan
zonedCorridor
multiWing
```

Unsupported combinations fail validation before candidate generation; they are not silently coerced.

Generated spaces use canonical `SpaceType + SpaceUsage` semantics.

## Cottage generator

Minimum inputs:

```text
floor count
basement option
attic/roof configuration
garage option
habitable room count
footprint
stair/core placement
topology family
```

The result is a candidate canonical project graph, not a special `ComposedBuilding` persistence mode.

## Building generator

Minimum inputs:

```text
building type
storey count
basement count
technical levels
roof configuration
apartments per floor
apartment mix
stair/lift cores
common corridors
technical/service rooms
floor-to-floor height
```

Repeated floors are independent canonical entities with stable IDs and explicit typical-floor lineage. No mutable aliasing is permitted.

## Residential complex generator

The residential-complex generator creates multiple canonical Building aggregates under one Site aggregate.

Minimum inputs:

```text
building count
building variants
site arrangement
courtyard configuration
parking/basement options
shared technical zones
building spacing
shared service-entry strategy
```

The result must preserve full composed semantics for every Building and remain compatible with ProjectRepository/Drift persistence.

## Deterministic template catalog

Template metadata:

```text
TemplateId
templateVersion
generatorVersion
family
displayName
parameter schema/type
constraints
```

Given the same template version, generator version and normalized typed parameters, generation must produce semantically equivalent geometry/topology.

Permanent entity IDs are not generated by string concatenation with floor numbers or labels.

## Candidate-first generation pipeline

The Wizard never mutates the live project during preview.

Required pipeline:

```text
Wizard UI
   ↓
Typed WizardParameters
   ↓
normalize + validate
   ↓
ProjectTemplateGenerator<P>
   ↓
GeneratedProjectCandidate
   ↓
CandidateGraphValidator
   ↓
ProjectDiff
   ↓
preview
   ↓
user confirms
   ↓
verify LocalProjectVersion
   ↓
assign/reuse stable permanent IDs through EntityIdFactory + generation mapping
   ↓
ProjectCommand / ProjectMutationSession
   ↓
atomic ProjectChangeSet + UndoRecord
   ↓
ProjectRepository save/autosave
```

Cancel leaves the live project semantic fingerprint unchanged.

## Proposed application contracts

Conceptually:

```dart
abstract interface class ProjectTemplateGenerator<P extends WizardParameters> {
  GeneratedProjectCandidate generate(P parameters);
}

final class GeneratedProjectCandidate {
  final ProjectCandidateGraph project;
  final GenerationManifest manifest;
  final ValidationReport validation;
  final WizardPreviewSummary summary;
}

abstract interface class CandidateGraphValidator {
  ValidationReport validate(ProjectCandidateGraph candidate);
}

abstract interface class ProjectDiffEngine {
  ProjectDiff compare(ProjectSnapshot current, ProjectCandidateGraph candidate);
}
```

`GeneratedProjectCandidate` represents the complete relevant candidate graph. Returning only `ProjectSite` is insufficient for multi-building, engineering, provenance and diff semantics.

## Preview identity rule

Preview IDs are draft-scoped.

They must not become persistent identities merely because a preview was rendered.

At commit, the system:

- preserves existing stable IDs for matched logical entities;
- allocates new IDs via `EntityIdFactory` for genuinely new entities;
- records semantic `generationKey` mappings;
- never derives persistent IDs from level numbers, indexes or display names.

## Preview requirements

Preview shows at least:

```text
site/building count
level count
room count
approximate areas
selected topology
warnings/blockers
2D/2.5D structural preview
engineering summary when enabled
```

The user can change parameters, regenerate the candidate, go back, confirm or cancel.

No preview action creates Undo history or increments the live project version.

## Geometry rules

Canonical generated geometry uses deterministic integer-mm coordinates.

Mandatory rules:

- no degenerate polygons;
- no unintended overlaps;
- rooms remain in intended envelopes;
- openings/cores require valid hosts;
- invalid geometry cannot commit;
- no platform-dependent floating-point semantics;
- boundary edges receive stable identity/lineage at commit.

## Engineering generation integration

Wizard architecture may generate architecture only or architecture plus selected engineering starter profiles.

Engineering generation is staged:

```text
classify spaces
→ place devices
→ build logical engineering graph
→ synthesize circuits/loops/distribution roles
→ create physical route candidates where supported
→ validate
→ preview diff
→ commit
```

POWER/LIGHTING/LAN/CCTV/ACS/FIRE generation must create logical relations, not only symbols.

Electrical sizing/protection that depends on jurisdiction, supply system, demand factors, installation method or other missing engineering inputs must remain blocked/warned rather than invented.

## Provenance and regeneration

Generated entities use field-aware provenance from the foundation contract:

```text
originType
generationId
templateId/templateVersion
generatorVersion
discipline
generationKey
overriddenProperties
lockedFromRegeneration
```

A single `userModified` boolean is not sufficient.

Regeneration always produces a candidate and diff before commit:

```text
ADD
UPDATE
PRESERVE
REMOVE
CONFLICT
```

Manual/overridden fields are preserved by default.

## Local-first and persistence compatibility

Wizard generation is fully offline.

Required dependency direction:

```text
Native UI
  ↓
Application/domain generator
  ↓
GeneratedProjectCandidate
  ↓
ProjectMutationSession
  ↓
Canonical ProjectAggregate
  ↓
ProjectRepository
  ↓
local persistence
  ↓
future Sync Engine
```

The Wizard must not depend directly on `EditorProjectDocument`, JSON files, `dart:io`, `path_provider`, SQLite APIs or backend HTTP calls.

Legacy JSON round-trip is tested through repository/codec adapters, not embedded in generator logic.

## Failure behavior

Generation is fail-closed for:

```text
unsupported parameter combination
invalid room count
degenerate/overlapping geometry
invalid hierarchy
invalid LevelId/BuildingId references
invalid structural-zone membership
broken opening/boundary-edge host
invalid vertical-core references
invalid engineering topology
duplicate permanent identity
stale LocalProjectVersion at commit
unresolved blocking conflict
```

Warnings may be shown in preview, but blocking validation cannot be bypassed silently.

## Implementation order

The authoritative umbrella order is `P0..P17` in `project-composition-foundation-decisions-v1.md`.

Wizard work is subordinate to that roadmap:


Wizard implementation cannot begin as direct mutation of the current `EditorBuildingWorkspace`.

## Non-negotiable conclusion

The Wizard is a deterministic, typed, candidate-first native authoring layer over the canonical ElecX ProjectAggregate.

It must preserve stable identity, atomic mutation, local-first behavior, field-aware provenance and cross-platform semantics while remaining independent from the persistence implementation and from any Web/browser architecture.
