# Spatial Editor Hardening — Acceptance Contract

This document is the acceptance source of truth for the interaction-hardening scope. New UI work must not bypass these contracts.

## 1. Canonical transaction lifecycle

Every persistent edit uses one transaction lifecycle:

`begin -> preview -> validate -> commit | cancel`

Applies to:
- component move/transform;
- cable endpoint reassignment;
- cable vertex editing;
- cable segment editing;
- future linear-luminaire geometry editing.

Acceptance invariants:
1. Preview must never create undo-history entries.
2. One user gesture produces at most one undo entry.
3. Cancel restores the exact pre-gesture persistent state.
4. Invalid preview is visible but not committable.
5. Mouse, keyboard, touch, stylus and precision-pad adapters must call the same session contracts.

## 2. Input arbitration

Hit-test priority for the select tool:

`cable endpoint -> cable vertex -> cable segment -> component handle/component -> marquee`

Two-finger touch remains viewport pan/zoom and must not commit an object edit.

Input-specific hit/snap radii are allowed, but persistent geometry remains surface-local millimetres.

## 3. Component transforms

`ComponentTransformSession` is the canonical component movement API.

Required behaviour:
- pointer drag, touch/stylus drag, keyboard nudge and precision-pad use the same transaction;
- active-surface bounds/profile validation happens during preview;
- Shift-axis constraints are preview constraints, not separate mutations;
- connected-route reroute may be previewed later, but component and affected routes must commit atomically when that capability is enabled.

## 4. Cable endpoint snapping

Cable endpoints are semantic, not free geometric endpoints.

Required behaviour:
- compatible `Port` targets outrank grid/geometry snaps;
- captured endpoint is centred on the resolved port anchor;
- magnetic capture uses acquisition/release hysteresis;
- incompatible ports cannot commit;
- endpoint reassignment and regenerated route geometry are one undoable operation;
- the opposite endpoint cannot be selected as the new target component.

## 5. Cable routing modes

### AUTO
- route geometry is generated by the routing engine;
- direct vertex/segment manipulation is disabled;
- endpoint relocation triggers automatic reroute;
- the best valid candidate is selected deterministically.

### ASSISTED
- engineer may drag vertices/segments;
- snapping and geometry assistance remain active;
- preview is continuously validated;
- warnings are allowed, errors are not committable.

### MANUAL + GUARDRAILS
- engineer controls geometry directly;
- editor does not silently normalize the user's intent except for required topological/orthogonal continuity;
- normative/geometric errors remain non-committable unless a future explicit override contract is introduced;
- no hidden override is allowed.

## 6. Cable handles

Required handles for a selected editable route:
- endpoint handles;
- interior vertex handles;
- interior segment handles.

Vertex drag semantics:
- arbitrary corner movement must create a real orthogonal dogleg around the target when a single corner cannot move while keeping both adjacent fixed legs orthogonal;
- the handle must never appear draggable while producing no geometry change.

Segment drag semantics:
- only interior runs are directly translatable;
- endpoint-adjacent runs belong to endpoint transformation;
- neighboring orthogonal legs must remain connected.

## 7. Lock and mandatory waypoint

- locked route segments cannot be modified by AUTO, vertex drag or segment drag;
- mandatory waypoints must survive optimization/autoroute;
- deleting a route removes orphaned route-edit metadata;
- lock/waypoint metadata is editor state and must be persistable before merge of the feature as production-ready.

## 8. Preview state and colours

Editor status meaning:
- green: valid and committable;
- amber: valid with warnings;
- red: invalid/non-committable.

Colour is supplementary; validation state must also be available as text/status for accessibility and debugging.

## 9. Project compass / daylight assist

`ProjectNorth` is project/site geometry, not decoration.

Required behaviour:
- one project north orientation is inherited by rooms, walls and windows;
- a daylight input must reference a wall;
- window geometry/transmittance inputs are validated;
- daylight reach is explicitly design-assist only;
- no lux, daylight-factor or normative PASS may be emitted by the heuristic engine;
- physical sun/photometric calculations require a separate context including geographic/time and photometric inputs.

## 10. LED strip / linear luminaire

LED strip is a `LinearLuminaire`, not a cable route.

It may reuse route-like geometry editing, but engineering semantics differ:
- cable route transfers energy/signal;
- linear luminaire consumes energy and emits light.

Minimum linear-luminaire parameters:
- nominal voltage;
- W/m;
- lm/m;
- maximum continuous length;
- cut step;
- profile width;
- allowed feed modes;
- optional driver reference.

Acceptance invariants:
- run length must be positive;
- run geometry is immutable from external collections;
- requested positive lengths never snap to zero;
- unsupported both-end feed is rejected;
- electrical summary derives total W, A and lm from actual run length;
- long runs report required feed sections.

Future voltage-drop/driver-sizing logic must be separate from the basic geometry summary and must not claim compliance before those calculations exist.

## 11. Normative boundary

`NormativeRouteEngine` currently provides geometric guardrails only. It is not proof of complete GOST/SP/PUE compliance.

Current valid scope:
- orthogonal routing;
- surface bounds/clearance;
- declared architectural obstacles;
- deterministic route scoring;
- warning/error result model.

Jurisdiction-specific requirements belong in a normative registry/rule layer and must remain outside Canvas widgets.

## 12. Merge gates

The hardening branch is not merge-ready unless all are true:
1. `dart format --output=none --set-exit-if-changed lib test` passes.
2. `flutter analyze` reports zero issues.
3. Full `flutter test` passes.
4. Acceptance tests cover endpoint priority, hysteresis, cancel/commit, invalid commit blocking, AUTO obstacle avoidance, vertex dogleg, segment drag, daylight input validation and linear-luminaire invariants.
5. No temporary one-shot workflow/helper remains.
6. No UI path bypasses the canonical edit session for persistent component/cable geometry mutation.
7. PR description explicitly distinguishes design-assist geometry from normative/photometric compliance.
